## 学习目标与前置条件

前置：能稳定运行实验地图和联机流程。目标是建立有基线的性能观察，并找到本机 Lyra 已有的观测入口。源码与配置核对于 2026-09-13，UE 5.8.1；本文不声称当前工程达到任何 FPS 或并发指标。

## 先固定实验条件

记录构建配置、分辨率、画质、地图、机器人/玩家数量、摄像机位置和测试时长。编辑器视口、PIE、新窗口与打包客户端的额外成本不同，不能混成一组数据。对首次加载/着色器准备与稳定运行分别测量。

## 操作步骤

1. 选固定路线或固定镜头，使用本教程的 **1920×1080、中等画质（Scalability 1）** 记录 Game、Draw、GPU 帧时间，而不只看平均 FPS。
2. 通过 Unreal Insights 采集 CPU 时间线，针对最慢的帧检查 Game Thread、任务和资源加载。调试截图和高频日志在测量期间关闭。
3. 对比一个客户端与两个客户端，单独观察服务器 Tick 和发送的数据量。客户端 GPU 忙不等于服务器逻辑慢。
4. 在同一场景切换隐藏/显示 HUD，检查 UI 是否有大量每帧属性绑定或重复 Tick；再看 Slate/UMG 性能数据。
5. 每次只调整一个系统，用相同场景复测中位数和慢帧。保留改变前后的设置与采样文件。

## Lyra 已有入口

`Source/LyraGame/Performance/LyraPerformanceStatSubsystem` 采集性能统计，`UI/PerformanceStats` 提供相应展示，`LyraGameSettingRegistry_PerfStats` 和画面设置关联用户选择。

`Config/DefaultEngine.ini` 使用 `LyraSignificanceManager`；相关意义分级可以帮助按对象重要性安排表现成本。启用某个管理器不代表全部自定义 Actor 自动做了预算控制，新增对象仍要明确接入策略。

动画成本应从网格数量、动画蓝图执行、更新频率和外观部件数检查。`ULyraAnimInstance` 使用 GameplayTagPropertyMap 和 GroundInfo，不意味着可无代价增加大量纯函数绑定或每帧世界查询。

## 复制方案不要按文件名猜

本机有 LyraReplicationGraph 源码和插件，但 `DefaultGame.ini` 的 `LyraReplicationGraphSettings` 明确配置 `bDisableReplicationGraph=True`，同时 DefaultEngine.ini 有 Iris 相关配置。**存在某套实现，不代表本次运行正在使用它。** 实际启用情况还要结合构建、配置覆盖和运行日志确认。

MMORPG 大范围对象复制需要围绕可见范围、更新频率和数据量设计。切到 ReplicationGraph 或 Iris 不会自动解决数据库访问阻塞、每帧全量遍历和无界 RPC。

## 从图中配置走到代码行为

### FPS 与毫秒先算清楚

一帧 16.67 ms 大约是 60 FPS，一帧 33.33 ms 大约是 30 FPS，这是 `1000 / 每帧毫秒` 的换算示例，不是本机测试结果。帧时间越长，等待下一帧越久；平均 FPS 可能掩盖偶发很慢的帧。
源码：`Source/LyraGame/Performance/LyraPerformanceStatSubsystem.cpp`，本机第 30–44 行。下面是实际节选；在 Rider 中按文件名和函数名定位，完整上下文以源文件为准。

```cpp
// Record stats about the frame data
{
	RecordStat(
		ELyraDisplayablePerformanceStat::ClientFPS,
		(FrameData.TrueDeltaSeconds != 0.0) ?
		1.0 / FrameData.TrueDeltaSeconds :
		0.0);

	RecordStat(ELyraDisplayablePerformanceStat::IdleTime, FrameData.IdleSeconds);
	RecordStat(ELyraDisplayablePerformanceStat::FrameTime, FrameData.TrueDeltaSeconds);
	RecordStat(ELyraDisplayablePerformanceStat::FrameTime_GameThread, FrameData.GameThreadTimeSeconds);
	RecordStat(ELyraDisplayablePerformanceStat::FrameTime_RenderThread, FrameData.RenderThreadTimeSeconds);
	RecordStat(ELyraDisplayablePerformanceStat::FrameTime_RHIThread, FrameData.RHIThreadTimeSeconds);
	RecordStat(ELyraDisplayablePerformanceStat::FrameTime_GPU, FrameData.GPUTimeSeconds);	
}
```

ClientFPS 使用 TrueDeltaSeconds 的倒数，并处理零值；FrameTime/GameThread/RenderThread/RHI/GPU 分别记录各部分时间，源码单位为秒。展示或制表时先换算成 ms，不要把 0.016 当作 0.016 毫秒。

Game、Draw/Render、GPU 可能并行工作，不能简单把各自时间相加当作真实整帧时间。先定位最限制帧输出的阶段，再用 Insights 时间线追具体任务。

### 新手的第一轮记录

在开发构建的游戏控制台输入 `stat unit` 查看帧时间，结束后再次输入关闭。控制台打不开时，用编辑器底部 Output Log 的 Cmd 输入；确认命令作用于预期世界。要分析细节，在 Unreal Insights 中打开本次采集，选中慢帧时间范围，再检查 Game Thread 与相关任务。

表格至少包含场景、构建、玩家数、Frame/Game/Draw/GPU 毫秒、是否首次加载、trace 文件位置。截图应保留时间范围与线程名称；一张没有坐标/时间单位的曲线无法让下一位读者判断。

**练习**：先比较 HUD 显示/隐藏，其他条件保持一致。若差异小于运行波动，记录“尚未观察到稳定差异”，不要为了给优化结论而挑一帧数字。

## 预期结果、排障与练习

交付一次优化时应能给出相同条件下的前后帧时间、最慢调用链与行为验证。若数据波动大，先延长稳定采样或排除后台编译，而不是继续加更多优化。

练习：为 1、10、50 个机器人设计测量表，分别记录客户端 CPU/GPU、服务器 Tick、内存和网络流量。不把此实验当作 MMO 最大并发证明；它只回答所选场景随对象数量变化的成本。


## 实例：功能通过之后继续检查音频日志

最终 Training Development 归档的两次原生运行都完成 11 项功能检查，但首轮 `game.log` 出现 AudioMixer 队列积压。`verification/training-package-log-analysis.json` 保留同一 exe 的两次日志 SHA、时序和实际计数；[打包验收章节](/docs/07-training/multiplayer-and-package#本次-package-与两次归档运行结果)保留首轮原图与准确范围。

本机 `AudioMixerSourceManager.cpp` 在命令队列扩容超过初始 **1 MiB** 阈值时记录 Error，并调用 `DoStallDiagnostics`；这不等于已经达到硬件重置阈值或发生崩溃。首轮抓到 `UpdatePendingReleaseData` 移除 SourceBuffer，继而在 `FMetasoundConstGraphGenerator` 析构中等待 `BuilderTask->EnsureCompletion`。已完成的音频解码任务与生成器内部图构建任务不是同一个完成条件，因此释放阶段仍可能等待。

诊断本身调用同步 `ThreadStackWalkAndDump`，Windows 实现会暂停被采样线程并进行取栈、符号化，之后恢复。两条日志之间约 8 秒的空白不能全部算成原始音频停顿；同时打印的 `Lyra_RingLoop_03` 是所有在途解码任务的枚举，不能直接断言该音效就是等待来源。第二轮同一归档无队列 Error/Stall，仍有一次 Underrun Display。首启负载或任务调度只是推测，尚不能据此宣布根因已经修复。

复现时保留声音与原设置，先用同一归档重复执行并对齐输入、资源加载和音频时间线。若继续出现，使用 Unreal Insights 的音频与任务轨迹核对等待中的 BuilderTask 及工作线程；记录诊断开销，分开评价功能结果与听感/帧时间。不要提高告警阈值、关闭声音或隐藏屏幕消息来制造“无错误”记录。
