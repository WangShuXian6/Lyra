## 学习目标与前置条件

本篇建立“输入 → RPC → 服务器能力 → 状态复制 → UI”的完整链路。先完成插件迁移，理解 ASC、GameplayAbility、GameplayEffect 和 Owner/Avatar。核对基准为本机 **UE 5.8.1 / 2026-09-13**，教学源码位于 `MMOGameplay.h/.cpp`。

## 为什么 ASC 放在 PlayerState

![真实 Designer HUD 显示奥术箭施放后法力 80、目标生命 60、剩余冷却 2.6 秒，目标反击使玩家生命降为 75](/media/mmorpg/mmo-A-skill.png)

图：2026-09-13 最终 Designer/Manny 运行轮次，UE 5.8.1，原生 1920×1080、Medium。角色类为 `/Game/Tutorial/BP_MMOCharacter`，奥术箭由 `/Game/Tutorial/GA_ArcaneBolt` 提供，字段显示来自 `/Game/UI/WBP_PlayerHUD` 的实际 MVVM 绑定。

本实验 `UMMOSpellAbility` 的实际结果：服务器确认施放，GameplayEffect 扣除 20 法力并产生冷却，目标生命从 100 变为 60；HUD 通过复制与 ViewModel 更新。UE 5.8.1，2026-09-13，1920×1080、中等画质，`/Engine/Maps/Entry` 加载 MMOCore 区域。

Lyra 的 `ALyraPlayerState` 创建 ASC，并使用 Mixed 复制模式。PawnExtension 把 PlayerState 作为 Owner、当前 Pawn 作为 Avatar。角色死亡或更换 Pawn 后，玩家身份、属性容器和服务器会话可以继续存在。

实验沿用这个职责划分：`AMMOPlayerState` 创建 `UMMOAbilitySystemComponent` 和 `UMMOAttributes`。服务器 `PossessedBy`、客户端 `OnRep_PlayerState` 都调用统一初始化函数。它们解决不同机器上的不同到达次序，不能只实现其中一个。

`UMMOPawnExtensionComponent` 管理 ASC 的 Avatar 与四阶段初始化。能力由 PlayerState 根据 PawnData 的 AbilitySets 在服务器授予，授予句柄也由 PlayerState 持有；换 Pawn 不重复授予，PlayerState 结束时统一撤销。只有 ASC 的当前 Avatar 仍是旧 Pawn 时，旧组件才清空 Avatar，避免延迟销毁抹掉新绑定。

```cpp title="MMOGameplay.cpp：服务器和客户端共享的 ASC 连接"
void AMMOCharacter::InitializeAbilitySystem()
{
    if (auto* PS = GetPlayerState<AMMOPlayerState>())
    {
        PawnExtension->InitializeAbilitySystem(PS->ASC, PS);
    }
    else
    {
        UninitializeAbilitySystem();
    }
}
```

上段在 PlayerState 存在时连接 Owner/Avatar，缺失时通过 `UninitializeAbilitySystem` 解除旧连接；PawnExtension 已由角色构造函数创建。`MMOExperienceGameplay.cpp` 中 `AMMOPlayerState::SetPawnData` 才调用 AbilitySet 的 `GrantToAbilitySystem`。实现需要 `MMOGameplay.h`、`AbilitySystemComponent.h`、`MMOPawnExtensionComponent.h`；模块依赖包括 GameplayAbilities、GameplayTags、GameplayTasks、MMOFramework。先在服务器授予，再生成 Pawn、完成组件初始化，最后把 `bSessionReady` 置为 true。

## 手工创建角色、技能和目标蓝图

在已成功构建的 MMORPG 编辑器中执行下面步骤；`prepare_content.py` 完成相同的创建、编译和保存。若资产已经生成，直接打开并核对，不要另建同名带数字后缀的资产。

1. Content Browser `/Game` 下新建 `Tutorial` 文件夹，右键 **Blueprint Class → All Classes**，搜索 `MMOCharacter`，创建 `BP_MMOCharacter`。打开 **Class Settings**，Parent Class 应为 `/Script/MMORPG.MMOCharacter`。
2. 在 Components 中展开继承组件：CapsuleComponent、CharacterMovement、Mesh、PawnExtension、SpringArm、Camera。选择 Mesh，Skeletal Mesh Asset 设 `SKM_Manny_Simple`，Animation Mode 为 Use Animation Blueprint，Anim Class 为 `ABP_MMOCharacter`；网格本地 Z 为胶囊半高的负值、Yaw=-90。准确来源与主图、层图创建步骤见[角色与动画](/docs/08-mmorpg/animation)。Class Defaults 确认 Replicates=true，Compile、Save。
3. 同一文件夹右键 Blueprint Class → All Classes，搜索 `MMOSpellAbility`，创建 `GA_ArcaneBolt`。Class Defaults 中查看 Instancing Policy=`Instanced Per Actor`、Net Execution Policy=`Server Only`、Cost Gameplay Effect Class=`MMOSpellCost`、Cooldown Gameplay Effect Class=`MMOSpellCooldown`。这些值继承自 C++，不要把 Cost/Cooldown 清空。Compile、Save。
4. 同样创建 `BP_MMOTrainingTarget`，父类 `MMOTarget`。Class Defaults 确认 Replicates=true；Components 里观察目标静态网格和碰撞。Health 初始 100 来自 `MMOGameplay.h`，该字段没有 EditAnywhere 标记，不能在 Details 中填写；运行时通过复制与目标 HUD 观察。Compile、Save。
5. 关闭三个资产编辑器，再从 Content Browser 打开，确认路径分别为 `/Game/Tutorial/BP_MMOCharacter`、`GA_ArcaneBolt`、`BP_MMOTrainingTarget`，编译状态为绿色。

`BP_MMOCharacter` 是 PawnData 实际选择的角色类，`GA_ArcaneBolt` 是 AbilitySet 的第二项能力，修改后会进入实际玩法。它们的连接点见下节。训练目标目前由区域组件创建原生 `MMOTarget`；`BP_MMOTrainingTarget` 保留为可替换子类教学资产，单独保存该子类不会替换区域组件的生成类型。

GameState 的 ExperienceManager 先异步加载依赖闭包，再激活 MMOCore；GameMode 同时等待 Experience Ready 和后端角色加载完成。PawnExtension 依次推进 Spawned、DataAvailable、DataInitialized、GameplayReady，本地玩家在 DataAvailable 收到输入资源后绑定动作。日志中应先出现 Experience Ready，再出现 `MMO GameplayReady character` 和客户端 `MMO input ready`。

UI 标签来自 `Config/DefaultGameplayTags.ini`，两个 Cooldown 标签由 `MMOGameplay.cpp` 的 UE_DEFINE_GAMEPLAY_TAG_STATIC 注册：Project Settings → Gameplay Tags 中检查 `Cooldown.MMO.Attack`、`Cooldown.MMO.Spell`、`UI.Layer.Game`、`UI.Layer.Menu`、`UI.Layer.Modal`、`UI.Slot.Status` 均存在。不要拼成不同大小写或漏掉层级；代码的 RequestGameplayTag 需要先有有效的标签注册。

## 属性复制与变化通知

`Health` 与 `Mana` 使用 `FGameplayAttributeData`，RepNotify 中调用 `GAMEPLAYATTRIBUTE_REPNOTIFY`。这一步不仅更新数值，还让 ASC 的属性委托得到变化通知，后面的 ViewModel 才能正确更新。

```cpp title="MMOGameplay.cpp：Mana 的 RepNotify"
void UMMOAttributes::OnRep_Mana(const FGameplayAttributeData& Old)
{
    GAMEPLAYATTRIBUTE_REPNOTIFY(UMMOAttributes, Mana, Old);
}
```

本切片最大生命和法力均为 100。真实项目若需要装备加成、等级成长和最大值变化，应增加 MaxHealth/MaxMana 属性，并明确最大值变化时当前值采用的规则。

## 标签如何找到已授予的技能

同一条 `InputTag.MMO.Spell` 连接两处资产：`DA_MMOInputConfig` 用它识别 `IA_Spell`，`DA_MMOAbilities` 用它标记授予的 `GA_ArcaneBolt`。PlayerState 创建 `UMMOAbilitySystemComponent`，AbilitySet 将标签写进 `FGameplayAbilitySpec.GetDynamicSpecSourceTags()`。按 2 或手柄左侧面键时，角色发送 `ServerActivate(InputTag.MMO.Spell)`；服务器从自己的 ASC 中查找已授予的 Spec，不接受客户端提交的技能类。

`AMMOCharacter::ServerActivate_Implementation` 只接受 Attack、Spell 两个白名单标签，并检查服务器权威、后端会话、Pawn 初始化、生命以及 PlayerState/ASC/当前 Avatar 的归属。通过后才调用下列完整函数。它位于 `MMOFramework` 模块的 `Private/MMOAbilitySystemComponent.cpp`，声明在同模块 `Public/MMOAbilitySystemComponent.h`；该头文件包含 `AbilitySystemComponent.h`，模块依赖 `GameplayAbilities`。`MMORPG` 依赖 `MMOFramework`，在 PlayerState 构造函数里用 `CreateDefaultSubobject<UMMOAbilitySystemComponent>(TEXT("ASC"))` 创建实例。

```cpp title="MMOAbilitySystemComponent.cpp：先收集句柄，再激活"
bool UMMOAbilitySystemComponent::TryActivateAbilitiesByInputTag(const FGameplayTag& InputTag)
{
    if (!IsOwnerActorAuthoritative() || !InputTag.IsValid()) return false;
    TArray<FGameplayAbilitySpecHandle> Handles;
    {
        ABILITYLIST_SCOPE_LOCK();
        for (const FGameplayAbilitySpec& Spec : GetActivatableAbilities())
            if (Spec.Ability && Spec.GetDynamicSpecSourceTags().HasTagExact(InputTag)) Handles.Add(Spec.Handle);
    }
    // Activation may invoke callbacks that add or remove specs. The list lock and traversal have ended.
    bool bAnyActivated = false;
    for (const FGameplayAbilitySpecHandle Handle : Handles)
        if (TryActivateAbility(Handle)) bAnyActivated = true;
    return bAnyActivated;
}
```

技能激活可能通过回调增删 Spec，因此不能一边遍历未保护的数组，一边直接激活。这个通用 ASC 会处理同一标签匹配的所有句柄；“每标签恰好一项、Input ID=-1”是当前两个教学技能的配置和验收约束，不是框架对未来组合技能的限制。

## 玩家受伤、死亡与检查点重生

实验中的训练目标在受到攻击且仍然存活时，会在下一帧用 `UMMOTargetRetaliation` 向攻击者施加一次真正的 GAS 即时效果，扣除 25 Health。下一帧执行让本次攻击先完成；生命归零时的 `CancelAllAbilities` 不会重入尚未结束的攻击能力。

1. 在内容浏览器打开 `/Game/Tutorial/BP_MMOCharacter`，Components 面板确认继承了 `HealthComponent` 和 `PawnExtension`。这些组件由原生父类创建，不要再添加第二份。
2. 打开 `/Game/Tutorial/GA_ArcaneBolt`，Class Defaults 中查看 Activation Blocked Tags 包含 `Status.MMO.Dead`。原生普通攻击也使用同一阻止标签；能力执行处还会验证生命、当前 Avatar 和 Pawn 初始化状态。
3. 打开 `/Game/MMO/BP_MMOGameMode`，Class Defaults → Respawn，将 Respawn Delay 保持为 `3.0` 秒。Compile、Save。Experience 和 PawnData 不需要更换。
4. 启动后端、独立服务器和两个客户端。让生命为 100 的玩家靠近一个满血目标，Tab 选中后间隔一秒按四次 1。每次目标存活时，玩家依次受到反击，生命变为 75、50、25、0。
5. 生命为零时确认移动和攻击停止，HUD 显示检查点重生信息；此时 P 或手柄 Menu 仍可打开设置，菜单和弹窗会继续阻止游戏输入。
6. 三秒后检查新角色在检查点出现，Health 恢复为 100。Mana、背包和经验保留；另一个客户端应观察到旧 Pawn 消失、新 Pawn 出现。

`UMMOHealthComponent` 只观察本 Pawn 的 ASC 生命委托。死亡状态复制到客户端后停用移动和胶囊碰撞；有 PhysicsAsset 的图形客户端显示布娃娃。服务端把重生计时器交给 GameMode。到期时，GameMode 解除旧 Pawn 的控制、销毁旧 Pawn、清除死亡标签，然后通过同一个 Experience/PawnData 生成新 Pawn。

PlayerState 和 ASC 始终保留，AbilitySet 由 PlayerState 授予一次。旧 Pawn 的 PawnExtension、HealthComponent 和动画实例解除各自的委托；新 Pawn 初始化完成后，Root ViewModel 重新观察新 Pawn，Designer 中已有的 MVVM 绑定继续接收 FieldNotify。不要在每次重生时再次 `GiveAbility`。

死亡等待期间离服也有明确规则：最终存档允许 Health 为零；下一次加载这种存档时，服务器将 Health 恢复为 100，并采用检查点位置。Logout 会清除旧连接的重生计时器，因此离线角色不会被旧异步回调重新生成。验证时应分别执行正常三秒重生，以及生命归零后立即从设置退出再入服。

源码定位：`MMOHealthComponent.h/.cpp`（生命观察与死亡复制）、`MMORespawnGameplay.cpp`（权威重生）、`MMOGameplay.cpp` 的 `LoadSnapshot`（死亡存档恢复）、`MMOUI.cpp` 的 `RefreshStatus`（本地化状态）。脚本的 `death-respawn` 轮会检查实际死亡观察、Pawn 替换、同一个 ASC、两项能力以及重生后的 Designer 绑定；最新实测结果以验证记录为准。

## 从图中配置走到代码行为

### 先从图中的一条技能记录读到服务器

前面的 DA_MMOAbilities 图里，普通攻击与奥术箭都使用 InputID=-1；它们靠 InputTag.MMO.Attack / Spell 匹配，不靠数字编号 1、2。数字键是 IMC 的物理按键，Input Tag 是玩法语义，AbilitySpec 是已经授予的能力记录。

沿“按 2 → IA_Spell → DA_MMOInputConfig → InputTag.MMO.Spell → 服务器分发 → ASC 匹配 Spec”逐个核对。本机两个技能为 ServerOnly，先由服务器决定是否执行。
源码：`examples/MMORPG/Plugins/MMOFramework/Source/MMOFramework/Private/MMOAbilitySystemComponent.cpp`，本机第 20–34 行。下面是实际节选；在 Rider 中按文件名和函数名定位，完整上下文以源文件为准。

```cpp
bool UMMOAbilitySystemComponent::TryActivateAbilitiesByInputTag(const FGameplayTag& InputTag)
{
    if (!IsOwnerActorAuthoritative() || !InputTag.IsValid()) return false;
    TArray<FGameplayAbilitySpecHandle> Handles;
    {
        ABILITYLIST_SCOPE_LOCK();
        for (const FGameplayAbilitySpec& Spec : GetActivatableAbilities())
            if (Spec.Ability && Spec.GetDynamicSpecSourceTags().HasTagExact(InputTag)) Handles.Add(Spec.Handle);
    }
    // Activation may invoke callbacks that add or remove specs. The list lock and traversal have ended.
    bool bAnyActivated = false;
    for (const FGameplayAbilitySpecHandle Handle : Handles)
        if (TryActivateAbility(Handle)) bAnyActivated = true;
    return bAnyActivated;
}
```

逐段解释：

1. `IsOwnerActorAuthoritative()` 要求权威端执行，标签无效也直接返回 false。
2. `ABILITYLIST_SCOPE_LOCK` 保护遍历；先把所有匹配标签的 Spec Handle 收集出来。
3. 退出小括号块，遍历已结束，再调用 TryActivateAbility。技能激活可能触发回调增删 Spec，因此不直接在遍历原数组时激活。
4. 返回 true 表示至少一次激活成功；当前两项配置各匹配一项，但通用函数并没有硬编码“一个标签只许一项”。

**怎么读数值图**：本章奥术箭截图的法力 80 表示从满值 100 消耗 20；目标生命 60 表示一次 40 伤害；玩家生命 75 来自目标反击 25。三项分别属于施法者 Mana、目标 Health 和施法者 Health，不是同一属性变化三次。

**完成检查**：在两客户端中分别观察自己的 Spec 和 Mana，确认按键来自 A 时没有直接修改 B 的角色状态。再做死亡重生，比较 Pawn 变更和 ASC 保持；重复 GiveAbility 会让配置正确的技能也出现重复实例。
