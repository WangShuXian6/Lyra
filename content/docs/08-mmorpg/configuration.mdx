## 学习目标与前置条件

本篇把配置表展开为可以在编辑器中逐步复现的操作。先完成[依赖迁移与首次 Editor 构建](/docs/08-mmorpg/migration)，确认打开的是 `F:/UE/LyraDocLabs/MMORPG/MMORPG.uproject`，原生 `MMOGameMode`、`MMOInputData` 等类已经可用。教程提供的 Config 已填好这些值；直接使用教学工程时逐项核对，迁入自己的空白工程时逐项设置。

以下截图均来自 **UE 5.8.1、2026-09-13 的真实 MMORPG 编辑器**。本轮在 Designer、Manny、Experience 和输入资产接入后，用原生 Slate 窗口采集；项目设置和资产窗口按字段数量展开，图片保留原始像素，尺寸不是游戏视口分辨率。点击图片可放大检查。采集时间、原始文件、PNG 哈希与当时的资产哈希记录在 `source-evidence/configuration-mmorpg.json`。来源清单保留初始配置的历史截图与报表生成前的 Dashboard 帧用于追溯；本篇操作使用更新后的实际字段，不要求读者照着历史值配置。

截图用于核对编辑器配置。修改 Config 后是否已重启、是否完成 Cook、运行时对象是否采用该资产，都在对应步骤分别检查；不能由一张 Class Defaults 图片推断游戏运行结果。

## 操作前先区分类、资产与正在运行的对象

类选择器中的名称通常省略 C++ 的 `U` / `A` 前缀。`MMOCharacter` 是 `AMMOCharacter` 原生类；`BP_MMOCharacter` 是继承它的蓝图资产；生成类路径末尾的 `_C` 表示该蓝图编译产生的类。三者不能互换。

| 项目 | 用途 | 本实验实际连接点 |
| --- | --- | --- |
| `MMOGameMode`、`BP_MMOGameMode`、`MMOGameInstance` | 原生规则、可配置规则子类与游戏实例 | Maps & Modes 选择 `BP_MMOGameMode` 和原生 `MMOGameInstance` |
| `/MMOCore/MMOCore` | GameFeatureData 数据资产 | 特性激活时执行 Add Components |
| `/Game/UI/BP_MMOUIPolicy` | 实际被加载的纯数据蓝图 | `DefaultUIPolicyClass` 引用其 `_C`，Layout Class 选择 `WBP_MMOLayout` |
| `BP_MMOCharacter` | 有 Mesh 和动画默认值的角色子类 | `DA_MMOPlayer.PawnClass` 引用其生成类，Experience 指向该 PawnData |
| `GA_ArcaneBolt` | 奥术箭技能子类 | `DA_MMOAbilities.GrantedAbilities` 引用其生成类，InputTag=`InputTag.MMO.Spell`、InputID=-1 |
| `BP_MMOTrainingTarget` | 原生目标的教学子类 | 当前区域组件直接生成原生 `AMMOTarget` |
| 七个 `WBP_*` 界面资产 | 可编辑 Designer 布局与 MVVM 绑定 | Policy 创建 WBP_MMOLayout，由它的 Class 字段选择各面板；ManaStatus 嵌套在 HUD Designer 中 |

如果需要让自己的蓝图子类参与运行，必须修改对应创建者的类引用，并再次验证 Cook 和运行结果。仅在内容浏览器创建或保存资产，不会替换 GameMode 的 DefaultPawnClass 或 ASC 中已有的 AbilitySpec。后端健康检查蓝图与实际 UMG/MVVM 绑定另见 [UI 蓝图工作流](/docs/09-mmo-ui/blueprint-workflow)。

## 一、设置地图、GameMode 与 GameInstance

先创建可配置的规则蓝图：

1. 在 Content Browser 的 `/Game/MMO` 右键 **Blueprint Class → All Classes**，搜索原生 **MMOGameMode**，命名 **BP_MMOGameMode**。
2. 打开蓝图，点击 **Class Defaults**，展开 **Experience**，找到 **Default Experience**。
3. 从主资产选择器选择 **DA_MMOExperience**，核对 ID 为 **MMOExperience:DA_MMOExperience**。如果列表为空，先完成 `/Game/MMO/Experiences/DA_MMOExperience` 生成，以及 Asset Manager 中 MMOExperience 类型的扫描配置，再重新打开选择器。
4. Compile、Save，关闭并重开核对这个 ID。它连接游戏规则和 Experience 数据；BP_MMOGameMode 的父类仍是 MMOGameMode。

![BP_MMOGameMode Class Defaults：Default Experience 为 MMOExperience:DA_MMOExperience](/media/configuration/mmorpg/game-mode-experience.png)

图：`/Game/MMO/BP_MMOGameMode` 的实际默认值。窗口同时显示 MMOGameState、MMOPlayerController 和 MMOPlayerState。这里继承的 Default Pawn Class 为原生 MMOCharacter；真正准入后生成的 Pawn 由 Experience 的 PawnData 选择 `BP_MMOCharacter`，不要为“名称一致”误改另一条创建路径。

随后设置项目入口：

1. 在主编辑器选择 **编辑（Edit）→ 项目设置（Project Settings）**。
2. 左侧选择 **项目 → 地图和模式（Maps & Modes）**。清空上方搜索框，点选“所有”，避免过滤器隐藏分类。
3. 展开“默认模式”，在“默认游戏模式”下拉框搜索并选择 **BP_MMOGameMode**，核对路径 `/Game/MMO/BP_MMOGameMode`。
4. 展开“默认地图”，分别打开“编辑器开始地图”和“游戏默认地图”的资产选择器，搜索 `Entry`，核对来源是 `/Engine/Maps/Entry`，不要选择同名用户地图。选择器看不到引擎内容时，在它的设置中开启 Show Engine Content。
5. 展开“默认地图”下方的“高级”，将 Server Default Map 也设为 `/Engine/Maps/Entry`。下图保留展开状态，分别检查三个地图字段。
6. 向下展开“游戏实例”，将“游戏实例类”设为 `MMOGameInstance`。点击其他字段提交选择，关闭并重新打开设置页确认值没有消失。

![Maps & Modes：BP_MMOGameMode、三个 Entry 地图与 MMOGameInstance](/media/configuration/mmorpg/project-maps-modes.png)

图：当前 MMORPG 的原生设置窗口。默认游戏模式为 BP_MMOGameMode，高级区域展开后显示 Server Default Map；三个 Entry 都来自 Engine 内容。

| 界面字段 | 值 | 为什么这样设置 |
| --- | --- | --- |
| Default GameMode | `BP_MMOGameMode` | 使用蓝图中的 Default Experience，并继承权威准入、存档与角色生成规则 |
| Editor Startup Map | `/Engine/Maps/Entry` | 编辑器打开这个空入口地图 |
| Game Default Map | `/Engine/Maps/Entry` | 客户端启动与返回登录使用入口世界 |
| Server Default Map | `/Engine/Maps/Entry` | Dedicated Server 使用相同区域入口 |
| Game Instance Class | `MMOGameInstance` | 建立 CommonGame 本地玩家体系；Experience Manager 负责特性激活 |

这些字段写入 `DefaultEngine.ini` 的 `[/Script/EngineSettings.GameMapsSettings]`：

```ini
[/Script/EngineSettings.GameMapsSettings]
EditorStartupMap=/Engine/Maps/Entry
GameDefaultMap=/Engine/Maps/Entry
ServerDefaultMap=/Engine/Maps/Entry
GlobalDefaultGameMode=/Game/MMO/BP_MMOGameMode.BP_MMOGameMode_C
GameInstanceClass=/Script/MMORPG.MMOGameInstance
```

项目设置会把已提交的值写入项目 Config；顶部“导出”是导出设置文件，不是保存当前工程所必需的按钮。完成本篇的项目类设置后保存资产、正常退出并重新打开 MMORPG，重新创建 GameInstance 和视口。Entry 中看不到手工摆放的区域是正常的：区域由 MMOCore 在游戏运行时生成。

## 二、选择 CommonUI 的视口类

1. 在 Project Settings 左侧点“所有设置（All Settings）”，清空前一页搜索。
2. 搜索 `GameViewportClient`，展开结果中的 **引擎 → 一般设置 → 默认类**。
3. 打开“游戏视口客户端类（Game Viewport Client Class）”下拉框，搜索并选择 `CommonGameViewportClient`。
4. 核对完整配置路径为 `/Script/CommonUI.CommonGameViewportClient`。它属于 CommonUI 模块，名称中的 CommonGame 不代表模块路径应写成 CommonGame。
5. 关闭再打开设置确认字段；完成其他项目类设置后正常重启编辑器。

![搜索 GameViewportClient 后，游戏视口客户端类为 CommonGameViewportClient](/media/configuration/mmorpg/project-common-viewport-client.png)

图：本轮原生设置窗口，只过滤出目标字段。右侧下拉值是 `CommonGameViewportClient`；源码对应 `DefaultEngine.ini` 的 `GameViewportClientClassName`。

| 字段 | 填写值 | 作用与核对 |
| --- | --- | --- |
| Game Viewport Client Class | `CommonGameViewportClient` | 让 CommonUI 输入路由接入游戏视口；重启后再运行客户端检查菜单操作 |

普通 GameViewportClient 不会因为启用了 CommonUI 插件就自动变成这个类。配置正确只证明创建入口正确，不能代替键盘、鼠标与手柄的运行验收。

## 三、选择 CommonLocalPlayer

1. 保持左侧“所有设置”，点击搜索框右侧清除按钮，再输入 `LocalPlayerClass`。
2. 展开 **引擎 → 一般设置 → 默认类**，打开“本地玩家类”下拉框。
3. 搜索并选择 `CommonLocalPlayer`，核对模块路径 `/Script/CommonGame.CommonLocalPlayer`。
4. 点击空白处提交选择，重开设置检查；同视口类一起重启编辑器，使新 LocalPlayer 使用该类。

![搜索 LocalPlayerClass 后，本地玩家类为 CommonLocalPlayer](/media/configuration/mmorpg/project-common-local-player.png)

图：本轮原生设置窗口。本地玩家类位于同一个 General Settings 默认类分组，但搜索过滤后只显示这一行。

| 字段 | 填写值 | 作用与核对 |
| --- | --- | --- |
| Local Player Class | `CommonLocalPlayer` | 向 UI 提供 PlayerController、PlayerState、Pawn 变化通知；切换角色时据此重新绑定 |

两个原生类的落盘配置应合并在同一个段中：

```ini
[/Script/Engine.Engine]
LocalPlayerClassName=/Script/CommonGame.CommonLocalPlayer
GameViewportClientClassName=/Script/CommonUI.CommonGameViewportClient
```

如果编辑器未关闭，不要同时在 Rider 修改同一 Config 再从设置窗口覆盖它。选择界面设置或关闭编辑器后编辑文件这条路径完成一次修改，再重开核对。

## 四、设置 Enhanced Input 的两个默认类

先设置 PlayerInput：

1. Project Settings → 所有设置，清空搜索后输入 `DefaultPlayerInputClass`。
2. 在 **引擎 → 输入 → 默认类** 打开“默认玩家输入类”下拉框，选择 `EnhancedPlayerInput`。
3. 确认值来自 `/Script/EnhancedInput.EnhancedPlayerInput`，点击其他位置提交。

![默认玩家输入类为 EnhancedPlayerInput](/media/configuration/mmorpg/project-enhanced-player-input.png)

图：本轮原生设置窗口。这里选择处理输入动作的 PlayerInput 类型。

再设置 InputComponent：

1. 清除搜索词，输入 `DefaultInputComponentClass`。
2. 打开“默认输入组件类”，选择 `EnhancedInputComponent`。
3. 核对 `/Script/EnhancedInput.EnhancedInputComponent`，关闭并重开设置页确认两个值；与前面项目类设置一起重启。

![默认输入组件类为 EnhancedInputComponent](/media/configuration/mmorpg/project-enhanced-input-component.png)

图：本轮原生设置窗口。它与上一张是两个独立字段，选择 PlayerInput 不会自动替你选择 InputComponent。

| 字段 | 值 | 作用 |
| --- | --- | --- |
| Default Player Input Class | `EnhancedPlayerInput` | 求值 Enhanced Input 映射与触发条件 |
| Default Input Component Class | `EnhancedInputComponent` | 角色 `SetupPlayerInputComponent` 用它绑定 Action 回调 |

```ini title="Config/DefaultInput.ini"
[/Script/Engine.InputSettings]
DefaultPlayerInputClass=/Script/EnhancedInput.EnhancedPlayerInput
DefaultInputComponentClass=/Script/EnhancedInput.EnhancedInputComponent
```

本教学使用 `/Game/MMO/Input` 中实际保存的七个 Input Action、`IMC_MMOPlayer` 和 `DA_MMOInputConfig`。PawnData 选择这份 InputConfig，原生 Hero 组件负责添加映射与绑定语义 Tag。逐个创建 Action、填写 17 个键位和 Modifier 的完整步骤见[角色与 GAS](/docs/08-mmorpg/character-gas)。

## 五、接通 CommonInput 的返回动作

1. 清空 Project Settings 搜索，左侧展开 **游戏 → 通用输入设置（Common Input Settings）**。
2. 展开“输入”，将“输入数据（Input Data）”选为原生 `MMOInputData`。
3. 勾选“启用增强输入支持（Enable Enhanced Input Support）”。页面中的平台输入、抖动参数不需要为本课程另建数据表。
4. 重新打开设置确认值，重启后运行客户端；打开设置、再打开退出确认，取消后核验返回到原设置层。

![Common Input Settings：Input Data 为 MMOInputData，Enable Enhanced Input Support 已勾选](/media/configuration/mmorpg/project-common-input.png)

图：本轮原生窗口。输入数据位于输入分组第一行，“启用增强输入支持”为该分组内已勾选的第三个布尔选项。

| 字段 | 值 | 代码连接点 |
| --- | --- | --- |
| Input Data | `MMOInputData` | `UMMOInputData` 构造函数创建 Boolean `UIBackAction` |
| Enable Enhanced Input Support | 勾选 | CommonUI 使用 Enhanced Input 返回动作 |

```ini title="Config/DefaultGame.ini"
[/Script/CommonInput.CommonInputSettings]
bEnableEnhancedInputSupport=True
InputData=/Script/MMORPG.MMOInputData
```

`UMMORootLayout` 为当前 LocalPlayer 把 Escape 与手柄 B 映射到这个返回动作，并在销毁时移除映射。截图证明字段配置，真实按键能否完成导航仍需[输入与焦点验收](/docs/09-mmo-ui/layers-input)。不要把没有配置 InputData 的 “no action provided” 错误归因于普通按钮颜色或布局。

## 六、让 Asset Manager 扫描 GameFeatureData

1. 清空搜索，在 **游戏 → 资产管理器（Asset Manager）** 展开“要扫描的主资产类型（Primary Asset Types to Scan）”。
2. 先检查是否已有 `GameFeatureData` 条目。已有则展开，缺少才点数组右侧 `+` 新增，避免重复扫描规则。截图中的数组索引由现有类型决定，你的索引可能不同，应按类型名定位。
3. 将“主资产类型”输入为 `GameFeatureData`，“资产基础类”选择原生 `GameFeatureData`。
4. 不勾选“拥有蓝图类”和“为仅编辑器”。展开“目录”，添加一项，选择 `/MMOCore` 插件挂载目录。
5. 展开“规则”，设置下表值；关闭再重开确认。保存项目其他资产后重启，再检查特性可发现。

![Asset Manager 展开 GameFeatureData、目录 /MMOCore 与 Rules，Cook Rule 为 Always Cook](/media/configuration/mmorpg/asset-scan-gamefeaturedata.png)

图：本轮原生设置窗口，展开顺序为主资产数组 → GameFeatureData → 目录 / 规则。此处扫描的是 Data Asset 实例，两个“蓝图类 / 仅编辑器”复选框均未勾选。

| 字段 | 值 | 解释 |
| --- | --- | --- |
| Primary Asset Type | `GameFeatureData` | 主资产类型标识 |
| Asset Base Class | `/Script/GameFeatures.GameFeatureData` | 要扫描的数据资产基类 |
| Has Blueprint Classes / Is Editor Only | 都不勾选 | 实例数据资产，并且运行时需要它 |
| Directories[0] | `/MMOCore` | 对应 Game Feature 插件内容，不是 `/Game/MMOCore` |
| Priority / Chunk ID | `-1` / `-1` | 保留本教学默认规则 |
| Apply Recursively | 勾选 | 递归应用规则 |
| Cook Rule | `Always Cook` | 将匹配的主资产纳入 Cook |

落盘位置为 `DefaultGame.ini` 的 `[/Script/Engine.AssetManagerSettings]`。`Always Cook` 不会保证全部引用都有效，也不证明一次 Cook 已成功；最终结果仍看独立 Cook 日志与产物。

### 为四类 MMORPG 数据资产添加扫描规则

GameFeatureData 不会自动扫描 Experience、PawnData 或 InputConfig。保持在 Asset Manager 页，对下面每一行分别新增或展开一个类型，填 Type/Base Class，展开 Directories 添加唯一目录，再展开 Rules。四项均不勾选 Has Blueprint Classes/Is Editor Only，Priority 和 Chunk ID 都为 `-1`，Apply Recursively 勾选，Cook Rule 为 Always Cook。

| Type | Asset Base Class | Directories[0] |

| MMOExperience | `/Script/MMOFramework.MMOExperienceDefinition` | `/Game/MMO/Experiences` |
| MMOPawnData | `/Script/MMOFramework.MMOPawnData` | `/Game/MMO/Pawns` |
| MMOAbilitySet | `/Script/MMOFramework.MMOAbilitySet` | `/Game/MMO/Abilities` |

## 七、配置并激活 MMOCore 数据资产

1. 关闭 Project Settings，打开 Content Browser；其 Settings 勾选 **Show Plugin Content**，在目录树选择 `MMO Core Training Zone Content`，即 `/MMOCore`。
2. 双击 `MMOCore`。若从空白开始尚无资产，在该根目录右键 **Miscellaneous → Data Asset**，类选择 `GameFeatureData`，名称填 `MMOCore`，再打开。核对对象路径 `/MMOCore/MMOCore.MMOCore`。
3. 结束 PIE 后再改配置。若上方 Current State 为 **Active** 或 **Loaded** 且出现不能编辑的提示，点击 **Registered** 并等待切换完成，再展开 Actions。下图就是停止 PIE 后的 Registered 状态；这一步改变编辑器的特性运行状态，没有替你保存数据。
4. 展开 **操作 → 动作（Actions）**。没有动作时点 `+`，选择 **添加组件（Add Components）**；展开动作索引 0 → 组件 → 组件列表（Component List），新增或展开索引 0。
5. 按字段表选择接收 Actor 类、组件类并勾选两端选项。点击左上保存或 Ctrl+S，再关闭资产并重新打开确认数据仍在。这个资产不是 Blueprint，不需要 Compile。
6. 数据保存后点击 Active 请求重新激活。运行游戏，Output Log 应看到 `MMOCore: zone added`；这证明组件实际进入世界，不能只以状态按钮颜色判断区域已创建。

![MMOCore Registered 状态下展开 Add Components：ModularGameStateBase 接收 MMOZoneComponent](/media/configuration/mmorpg/feature-data-actions.png)

图：`/MMOCore/MMOCore` 的本轮原生资产窗口。操作 → 动作 → 索引 0 → 组件 → 组件列表 → 索引 0 已逐层展开；Client Component 和 Server Component 都勾选。

| 字段 | 值 | 作用 |
| --- | --- | --- |
| Actor Class | `/Script/ModularGameplayActors.ModularGameStateBase` | 接收组件请求的模块化 GameState 基类 |
| Component Class | `/Script/MMOCore.MMOZoneComponent` | 原创区域生成组件 |
| Client Component | 勾选 | 客户端建立同一套几何体、碰撞和视觉场景 |
| Server Component | 勾选 | 服务器建立碰撞和权威训练目标 |

初始状态配置在 `MMOCore.uplugin` 的 `BuiltInInitialFeatureState` 中，当前值为 **Registered**；顶部“初始状态”的文字不是让读者直接输入的新字段。运行时 `UMMOExperienceManagerComponent::ActivateFeatures` 根据 DA_MMOExperience 的 `GameFeaturesToEnable` 数组请求加载激活，并等待完成后进入 Ready。区域由 C++ 使用引擎基础形状生成，没有另一张名为“MMOZone”的地图需要创建。

固定地板与墙体的创建在 `MMOZoneComponent.cpp::BeginPlay`。服务器和客户端生成相同的六块几何体，名称固定为 `MMOZone_Floor`、四面 `MMOZone_Wall*` 和 `MMOZone_Obstacle`。`FActorSpawnParameters.Name` 填明确名称，`NameMode` 使用 `Required_ErrorAndReturnNull`，`bDeferConstruction=true`；在 `FinishSpawning` **之前**调用 `SetNetAddressable`，设置网格、碰撞与尺寸后把 Mobility 设为 `Static`。这些值由 C++ 生成，不需要创建同名蓝图或手工添加第二份场景。

这一步关系到联机移动：自动生成的 Actor 名称在打包客户端与服务器中可能不同，不能把它们当作可互相查找的对象。角色站在地面上时，CharacterMovement 会处理移动基座引用；本教程固定场景使用相同路径和静态属性，避免未解析的基座导致服务器位置修正被丢弃。运行日志应出现六个 `MMO_ZONE_GEOMETRY` 稳定名称，不应出现 `Unable to resolve default guid` 或 `could not resolve the new relative movement base actor`。这个规则只适用于本例各端一致的固定场景；会移动的平台应由服务器管理并复制其状态，不能通过改成 Static 来省去复制。

## 保存后的整体验证

保存所有修改的 Blueprint/Data Asset，检查没有未保存标记，然后正常退出并重新打开 MMORPG。逐项确认地图类、输入类、UI Policy 与 MMOCore 数据没有恢复为默认值。菜单里的 Export Settings 与复制截图均不能替代资产保存。

启动顺序是 PostgreSQL → Backend Program → Dedicated Server → 两客户端，具体命令见[双客户端运行](/docs/08-mmorpg/run-lab)。客户端先看到登录层；入服后看到区域与 HUD；选择目标并施法时，法力、冷却与目标生命值应按权威结果更新。配置截图证明编辑器中的字段和来源，游戏运行、原生蓝图编译、Cook 与原生输入事件分别由对应验证记录证明；实体 USB/蓝牙手柄兼容性仍需在目标设备检查。

| 现象 | 首先回到哪一步 |
| --- | --- |
| 找不到 MMO 原生类 | 确认 MMORPGEditor 构建成功、工程身份正确，重新加载工程 |
| 只有 Entry 空世界 | Asset Manager 扫描与 MMOCore Add Components / 激活结果 |
| 登录 UI 完全没有出现 | CommonLocalPlayer、CommonGameViewportClient、UI Policy 生成类引用 |
| 角色输入不能绑定 | EnhancedPlayerInput 与 EnhancedInputComponent 两个默认类 |
| 返回操作没有 Action | CommonInput 的 InputData 与 Enhanced Input 支持 |
| 修改教学子类但运行结果不变 | 回查 GameMode、区域生成和 GiveAbility 实际引用的类 |

练习：在独立副本中记录一个字段的“界面值 → Config/资产值 → 创建对象 → 游戏结果”。先选 GameViewportClient 或 Layout Class，不要同时改多个配置；一次验证只改变一个连接点，便于定位原因。

源码：`examples/MMORPG/Config/DefaultInput.ini`，本机第 1–3 行。下面是实际节选；在 Rider 中按文件名和函数名定位，完整上下文以源文件为准。

```ini
[/Script/Engine.InputSettings]
DefaultPlayerInputClass=/Script/EnhancedInput.EnhancedPlayerInput
DefaultInputComponentClass=/Script/EnhancedInput.EnhancedInputComponent
```

方括号是配置节，表示要配置哪一个反射类。等号左边是属性名，右边 `/Script/模块.类` 是原生类路径；C++ 类名前缀 `U` 不写进这个反射路径。这三行分别对应本章的默认输入类两张截图。

`Default*.ini` 是项目默认配置，`Saved/Config` 是本机/运行生成的覆盖。字段改了又恢复时，应查配置层级和保存结果，不要随意把整份 Saved Config 复制到项目默认文件。数组配置中的 `+` 表示追加条目，`!属性=ClearArray` 表示清空继承数组；它们不是注释。

### 按用途复查本章的十四组截图

| 组别 | 先看哪几个图中字段 | 失败会出现什么 |
|---|---|---|
| 启动与类型 | Entry 地图、BP_MMOGameMode、MMOGameInstance | 加载了错误世界，或没有业务 GameInstance |
| 本地玩家和输入 | CommonLocalPlayer、CommonGameViewportClient、EnhancedInput 两类 | 界面路由/玩家子系统/输入绑定不正确 |
| 资产发现 | Primary Asset Type、Base Class、Has Blueprint Classes、Directories | 能看到文件，却用 PrimaryAssetId 找不到它 |
| Feature 装配 | Add Components 的 Actor/Component 与客户端/服务端开关 | 区域组件没有出现在正确世界 |
| 展示 | Policy.LayoutClass、Mesh.AnimClass、复制字段 | 有角色数据但模型/界面/远端显示不对 |
| 构建内容 | Maps to Cook、目录与 DX12/SM6 | 编辑器可运行，归档缺资源或着色格式不匹配 |

不要一次改十四组然后才测试。每组都按“选对对象 → 展开具体字段 → 保存 → 重开确认 → 检查对应日志/行为”推进。重启要求以实际面板提示为准；蓝图 Class Defaults 变化先 Compile、再 Save，普通 Data Asset 没有 Compile。

**小练习**：在不改数值的情况下，把一个原生类路径、一个蓝图生成类路径、一个普通数据资产路径各抄一条，分别指出 `/Script/...`、`_C` 与普通对象引用的差别。不要给 Data Asset 随意加 `_C`。
