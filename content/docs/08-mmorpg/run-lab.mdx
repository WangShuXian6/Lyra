## 学习目标与前置条件

本篇把“代码编译成功”推进到“两个独立客户端真正共享服务器状态”。需要完成 MMORPG Editor 构建、运行 `prepare_content.py`、初始化数据库，并构建和启动 Backend Program。使用本机 UE 5.8.1；以下命令中的目录按实验准备脚本实际输出调整。

源码工程和产物目录分开：文档仓库保存原创源码、教程与脚本，`LyraDocLabs` 保存导入的官方插件、生成资产和构建缓存。UE 编辑器与 Rider 同时打开时，先结束 Live Coding 会话再进行完整 UBT 构建。

## 启动顺序

1. 启动 PostgreSQL，确认后端使用专用角色和教学数据库。
2. 启动 Backend Program，检查健康接口和数据库迁移状态。
3. 给游戏服务器进程设置与后端匹配的 `MMO_SERVER_SECRET`，启动 Dedicated Server。
4. 启动两个独立游戏客户端。每个客户端分别注册账号、创建不同角色，再进入 `local-1`。

开发期可以用 Editor 二进制分别启动服务器与游戏进程，不需要先等待全套发布打包：

```powershell title="推荐入口：一个服务器与两个可见客户端"
pwsh -File F:/UE/LyraDoc/scripts/mmorpg/Start-Lab.ps1
```

脚本等待游戏服务器监听 7777 且 MMOCore 场景注入完成，再打开客户端。它把服务器身份只放入服务器子进程环境，客户端明确移除 `PG*` 和 `MMO_SERVER_SECRET`；不需要在游戏进程中配置数据库。默认窗口为 1920×1080、中等画质，并在实验工程 `Saved/Logs/Interactive` 保存进程清单和本地日志。`-ClientCount 1` 可先单窗口检查；只有确认 7777 上是本实验服务器时才使用 `-UseRunningServer`。

理解底层命令时，可以在两个独立终端分别启动服务器和客户端。服务器终端先运行 `. F:/UE/LyraDoc/scripts/backend/Common.ps1` 与 `Import-MMOGameServerEnvironment`；客户端使用干净终端：

```powershell title="独立游戏服务器（开发验证）"
& 'E:/UnrealEngine/Engine/Binaries/Win64/UnrealEditor.exe' `
  'F:/UE/LyraDocLabs/MMORPG/MMORPG.uproject' `
  /Engine/Maps/Entry -server -port=7777 -log
```

```powershell title="客户端 A；再启动一次作为客户端 B"
& 'E:/UnrealEngine/Engine/Binaries/Win64/UnrealEditor.exe' `
  'F:/UE/LyraDocLabs/MMORPG/MMORPG.uproject' `
  /Engine/Maps/Entry -game -windowed -ResX=1920 -ResY=1080 -ForceRes
```

这两个命令不会自动启动后端，也不会代替 `MMORPGClient`、`MMORPGServer` 的构建与 Cook 验收。发布产物必须单独检查缺失资产、默认地图和 ServerOnly 模块隔离。

## 独立目标、Cook 与实际产物启动

1. 保存并正常关闭编辑器，确认所有使用同一引擎的 Live Coding 会话已结束。
2. 依次构建下方 Client、Server 两个目标；每次等 `Result: Succeeded` 后再执行下一条。源码引擎还需构建 `UnrealPak` 和 `BootstrapPackagedGame`，分别供 Pak/IoStore 打包和生成 Windows 顶层启动程序使用。首次编译需要引擎单体库，耗时与 Editor 增量构建不同，建议把构建 Intermediate 放在 SSD。
3. 重新核对原创 UI 资产已生成，尤其 `/Game/UI/WBP_ManaStatus` 的两条绑定已编译。Packaging 中地图为 Entry，Always Cook 目录为 `/MMOCore`、`/Game/UI`、`/Game/MMO` 和 `/Game/Localization`。再完成[健康检查蓝图的显式 Cook 标签](/docs/09-mmo-ui/blueprint-workflow#为健康检查蓝图声明-cook-依赖)：`DA_TutorialExamples` 只包含 BP_BackendHealth，不包含 Tutorial/Tests 的验证副本；配置变更后重启编辑器。
4. 执行 `scripts/mmorpg/Package-Lab.ps1`。脚本使用 UAT BuildCookRun 的 Client+Server Cook/Stage，输出 WindowsClient 与 WindowsServer 两套目录，并检查客户端不包含 libpq、libsodium、服务端私有模块或后端口令文件。
5. 用 Stage 输出的实际两个 exe 路径运行 Invoke-Smoke；此时传入的是 cooked 原生 Client/Server，不能传 UnrealEditor.exe 冒充。等待 combat、restore、death-respawn、ui-return 四轮共八个结果完成，再检查 `verification/mmorpg-packaged-smoke.json`。随后用相同两个 exe 参数加 `-DeathLogoutOnly`，单独验证死亡等待中退出的恢复策略。

```powershell title="原生 Client 与 Server 构建"
& E:/UnrealEngine/Engine/Build/BatchFiles/Build.bat `
  MMORPGClient Win64 Development `
  -Project=F:/UE/LyraDocLabs/MMORPG/MMORPG.uproject `
  -WaitMutex -NoHotReloadFromIDE -MaxParallelActions=3 -NoUBA
& E:/UnrealEngine/Engine/Build/BatchFiles/Build.bat `
  MMORPGServer Win64 Development `
  -Project=F:/UE/LyraDocLabs/MMORPG/MMORPG.uproject `
  -WaitMutex -NoHotReloadFromIDE -MaxParallelActions=3 -NoUBA
& E:/UnrealEngine/Engine/Build/BatchFiles/Build.bat `
  UnrealPak Win64 Development `
  -WaitMutex -NoHotReloadFromIDE -MaxParallelActions=3 -NoUBA
& E:/UnrealEngine/Engine/Build/BatchFiles/Build.bat `
  BootstrapPackagedGame Win64 Shipping `
  -WaitMutex -NoHotReloadFromIDE -MaxParallelActions=3 -NoUBA
# 首次准备源码引擎的 AutomationTool 与平台脚本模块。
& E:/UnrealEngine/Engine/Build/BatchFiles/RunUAT.bat -CompileOnly
if ($LASTEXITCODE -ne 0) { throw 'AutomationTool preparation failed; inspect the first build error.' }
pwsh -File F:/UE/LyraDoc/scripts/mmorpg/Package-Lab.ps1
```

本机源码引擎已经编译 AutomationTool 和 Windows 平台脚本，并配置可用的 Windows SDK。上面的 `RunUAT.bat -CompileOnly` 是首次准备这些工具的独立步骤；执行前正常关闭共享引擎的编辑器，并等待其他构建结束。预期退出码为 0，且引擎下存在 `Engine/Binaries/DotNET/AutomationTool/AutomationTool.dll` 与 `Engine/Binaries/DotNET/AutomationTool/AutomationUtils/net10.0/AutomationUtils.Automation.dll`。工具已经就绪且没有变化时无需重复准备；缺失时执行这条命令，不能只跳过打包脚本的检查。相同前置流程见 [训练场打包工具准备](/docs/07-training/multiplayer-and-package)。

`Package-Lab.ps1` 在检查程序集后使用原生 `-NoCompileUAT -NoCompile -NoAutoSDK` 参数，直接执行已有工具；这些参数不跳过资产 Cook、着色器编译、Stage 或 Pak/IoStore。它们属于后续打包阶段，**不要附加到允许工具编译的 `-CompileOnly` 准备命令**。

```powershell title="已 Cook 的独立二进制验收"
pwsh -File F:/UE/LyraDoc/scripts/mmorpg/Invoke-Smoke.ps1 `
  -ClientExecutable F:/UE/LyraDocLabs/MMORPG/Saved/StagedBuilds/WindowsClient/MMORPG/Binaries/Win64/MMORPGClient.exe `
  -ServerExecutable F:/UE/LyraDocLabs/MMORPG/Saved/StagedBuilds/WindowsServer/MMORPG/Binaries/Win64/MMORPGServer.exe `
  -RestartBackendBetweenRounds
```

`Package-Lab.ps1` 的成功报告只说明 Cook、Stage 和客户端边界检查完成，`gameplayExecuted=false`；只有后续实际执行 smoke 才能说明打包产物完成账号、复制、技能、存档与 UI 返回。发布时以两份实际报告为准，不能用构建命令存在代替执行结果。

图形与国际化还需要在这两个真实产物上单独验证。沿用相同路径运行：

```powershell title="Cook 后的 Designer、动画、中文字体与语言重启验证"
pwsh -File F:/UE/LyraDoc/scripts/mmorpg/Invoke-RenderedShowcase.ps1 `
  -ClientExecutable F:/UE/LyraDocLabs/MMORPG/Saved/StagedBuilds/WindowsClient/MMORPG/Binaries/Win64/MMORPGClient.exe `
```

该模式不会给游戏程序传 `.uproject` 或 `-game`，也不读取 Editor DLL 作为产物证据。先用原生 UnrealPak 检查实际发布目录包含 `MMO.locmeta`、en/zh-Hans 的 `MMO.locres`、Roboto 和中文后备字体 DroidSansFallback；然后检查 22 张 1920×1080、中等画质的真实视口图、画质按钮后的分辨率、移动时实际 BlendSpace 节点，以及两个独立客户端的语言落盘和新进程中文/英文登录标题。结果写入独立的 `verification/mmorpg-packaged-rendered-showcase.json`，保留 Editor 开发验证报告。还需目视中文截图确认字形，不能只凭文本变量有中文就认定字体显示正常。

本版 Windows 客户端使用 **DirectX 12 / Shader Model 6**，需要相应显卡与驱动。配置在 `Config/Windows/WindowsEngine.ini`：Default RHI 选 DirectX 12，D3D12 Targeted Shader Formats 仅保留 `PCD3D_SM6`，D3D11 与 Vulkan 格式列表清空。编辑器中对应 **Project Settings → Platforms → Windows**。这项选择决定 Cook 的着色器平台；设置页的 Medium 控制的是另一组运行时画质参数，仍保持十组等级为 1。首次 Cook 只编译本版实际支持的一套格式，脚本同时将 ShaderCompileWorker 限制为两进程。

## UI 验收

检查登录表单的 Tab 顺序、角色下拉框、按钮可达性。进入游戏后，HUD 允许玩法与鼠标界面并行；打开背包/设置后，菜单层应接管输入；再打开退出确认，Modal 层成为最高优先级。取消后焦点应回到上一层。

键鼠和手柄都需要实际操作。手柄按键映射存在并不等于所有导航已经验收；编辑器中鼠标点击成功，也不能代替焦点恢复和返回操作测试。

**2026-09-13 原生输入验证：17/17 项通过。** `verification/mmorpg-native-ui-input.json` 汇总 114 次原生 Slate 输入操作及对应观察，包括 P/I、手柄 Menu/View、方向键导航、A 确认、B/Escape 返回、模态焦点恢复、退出后重新登录和角色切换。药剂通过真实按钮操作使 Mana 从 40 变为 80、背包数量从 1 变为 0，Designer 绑定随之更新。这是引擎原生键鼠/手柄事件注入，未连接物理手柄硬件。后半段 PIE 窗口因当时的画质按钮同时应用分辨率而变为 1914×1042，该部分只用于输入与生命周期验证，不计为 1920×1080 素材验收；修正后的画质与图像尺寸由独立渲染回归检查。

## 日志与证据

自动回归入口为 `scripts/mmorpg/Invoke-Smoke.ps1 -RestartBackendBetweenRounds`。默认用 NullRHI 启动两个独立客户端，真实完成 HTTP 登录、入服票据、共享目标伤害、GAS 消耗/冷却、背包隔离、移动复制，以及后端重启后退出重进的快照验证。第三轮通过实际 GAS 反击让两名玩家死亡，检查权威重生、同 ASC、两项能力及重生后的 Designer 绑定。第四轮调用设置面板的退出确认逻辑，再检查 OpenLevel 后登录层恢复、Game/Modal 层清空。它只把脱敏的 `MMO_SMOKE_RESULT` 写入验证 JSON；原始本地日志可能包含一次性 travel ticket，不应直接发布。

`Invoke-Smoke.ps1 -DeathLogoutOnly` 使用另外一组临时账号，保留战斗获得的药剂，在真正死亡后调用 Settings → Confirm 正常离服。脚本等待实际 final save 和 release 回调，通过账号接口核对存下的 Health 确实为零，再启动新客户端检查生命 100、检查点、原法力/经验/药剂。结果写入独立的 `verification/mmorpg-death-logout.json`，不与普通三秒重生结果混用。

这个无图形回归用于验证逻辑，不能代替游戏截图与 UI 导航测试。传入 `-Visible` 才运行可见图形预览；所有图形预览统一 **1920×1080、中等画质（Scalability = 1）**。脚本只给服务器进程传入服务身份，客户端环境移除 PostgreSQL 与服务器 secret；测试结束后清理本轮确切账号名单。

素材采集入口为 `scripts/mmorpg/Start-Lab.ps1 -Showcase`。它创建专用教学账号与角色，通过真实 HTTP 入服，使用真实 GAS 能力攻击，再由引擎 Slate 截图 API 采集含 UMG 的 `SViewport`：登录、HUD、技能、背包、设置和模态确认。调用发生在游戏定时器中，避开当前引擎 `ProcessScreenShots` 内嵌 Slate 重绘导致的阻塞。流程结束后客户端继续停留在游戏中，便于继续实际操作；截图位于实验工程 `Saved/Screenshots/MMOShowcase/<本轮编号>`。`-RenderOffscreen` 仅隐藏窗口，仍使用真实 RHI 渲染。

采集结束运行 `scripts/mmorpg/Stop-Lab.ps1 -Manifest <启动输出的进程清单>`，正常关闭本轮客户端、等待最终保存，再关闭本轮创建的服务器并删除确切的教学账号。脚本核对进程 PID、启动时间与可执行文件，避免误关其他 UE 项目。截图脚本中的程序化点击和焦点记录不等于人工键鼠/手柄导航验收，仍需单独执行上一节的操作。

语言保存使用 `Invoke-RenderedShowcase.ps1` 验证。A 从英文开始最终保存简体中文，B 从中文开始最终保存英文；每个客户端拥有独立 INI。脚本随后读取磁盘，再启动不传 `-culture` 的新进程，确认登录页使用刚保存的语言。源码引擎的 `-Multiprocess` 默认禁止写配置，故这些独立配置的进程显式加 `-MultiprocessSaveConfig`；离屏预览再用 `-ForceRes` 阻止虚拟显示尺寸把视口缩小。这两项参数都在实际截图尺寸和重启测试中核验。

至少保存构建目标、退出码、启动命令、后端响应、服务器准入与保存日志，以及两客户端同场截图。截图需注明是开发进程还是发布产物。蓝图图使用原生导出的节点文本和 1:1 图截图；像素缩放后的屏幕预览不能替代可读的节点原图。

## 常见问题与练习

- **Cook 已成功，但 Stage 报 Zen readiness 超时**：先分别检查本机 Zen 健康接口和 UAT 日志。本机首次失败是 .NET 代理没有把 IPv6 URI 主机 `[::1]` 视为已有 `::1` 例外，健康请求经代理返回 502，直连则为 200。`Package-Lab.ps1` 保留现有 NO_PROXY 条目，只在本次进程及 UAT 子进程中补 localhost、127.0.0.1、::1、[::1]，结束后恢复原值。没有修改系统代理。只有确认前次 Cook 成功且资产、Cook 配置未变，才使用 `-SkipCook` 重做 Stage；本机失败和恢复链均保留在 Package 报告中。
- **首次 DX12/SM6 启动停留在启动画面**：先查看日志是否正在编译 WorldGrid 等默认材质，并检查 ShaderCompileWorker 的 CPU、内存和系统可用内存。首次着色器缓存缺失时，主日志可能暂时不更新；仍在计算不等于死锁。等待完成后保留生成缓存，后续启动会复用它。脚本限制编译线程只控制负载，不会跳过必须生成的着色器。
- **登录按钮报连接错误**：检查 8088 端口、后端健康状态和 `-MMOBackend=` 参数；不要去修改 UE 网络端口。
- **连不上游戏服务器**：检查 7777 端口、服务器进程以及一次性票据是否已过期。
- **看到空白界面**：检查 `/Game/UI/BP_MMOUIPolicy` 存在，DefaultGame.ini 指向正确类，CommonGame 的 LocalPlayer/GameInstance 配置正确。
- **特性未就绪**：检查 `/MMOCore/MMOCore` 资产、插件发现和 Add Components 的接收者类。
- **第二次入服提示角色正在使用**：查看前一次 final save/release 是否完成，或等待租约过期后重试。

练习：让两位读者各操作一个客户端，按验收表互相观察，并把发现的差异记录为带复现步骤的缺陷。以新角色重跑整个流程，防止旧数据掩盖初始化错误。

## 从图中配置走到代码行为

### 为什么已登录还可能没有角色
源码：`examples/MMORPG/Source/MMORPG/Private/MMOExperienceGameplay.cpp`，本机第 63–79 行。下面是实际节选；在 Rider 中按文件名和函数名定位，完整上下文以源文件为准。

```cpp
void AMMOGameMode::TryStartPlayer(APlayerController* Controller)
{
    auto* PS = Controller ? Controller->GetPlayerState<AMMOPlayerState>() : nullptr;
    auto* Experience = UMMOExperienceManagerComponent::FindExperienceManager(GetWorld());
    if (GetNetMode() != NM_DedicatedServer || !PS || !PS->bCharacterLoaded || Controller->GetPawn()
        || !Experience || !Experience->IsExperienceReady()) return;
    if (!PS->SetPawnData(Experience->GetPawnData()))
    { CastChecked<AMMOPlayerController>(Controller)->ClientBackendError(TEXT("pawn_data_invalid")); Controller->Destroy(); return; }
    RestartPlayerAtTransform(Controller, FTransform(FRotator::ZeroRotator, PS->SavedPosition));
    if (auto* Pawn = Cast<AMMOCharacter>(Controller->GetPawn()); Pawn && Pawn->PawnExtension->IsPawnReady())
    {
        PS->bSessionReady = true; PS->OnRep_Progress(); PS->ForceNetUpdate();
        UE_LOG(LogTemp, Display, TEXT("MMO GameplayReady character %s: Experience + persistence + Pawn InitState"), *PS->CharacterID);
    }
    else
    { CastChecked<AMMOPlayerController>(Controller)->ClientBackendError(TEXT("pawn_initialization_failed")); Controller->Destroy(); }
}
```

入口同时检查 Dedicated Server、PlayerState、角色存档已加载、尚未拥有 Pawn、Experience Ready。缺一项就先返回。准备完成后 SetPawnData 授予技能集，再从 SavedPosition 生成角色；PawnExtension 也就绪才设置 bSessionReady。

所以“HTTP 登录成功”“获得入服票据”“服务器兑换票据成功”“角色 GameplayReady”是四个不同检查点。日志停在哪一步，就读哪一步的数据，不要反复点击登录生成更多并行请求。

| 你看见的现象 | 首个检查位置 | 对应章节 |
|---|---|---|
| 注册/登录界面显示连接错误 | Backend Program 是否监听；客户端 Base URL | 后端运行与测试 |
| 票据成功但连接不上世界 | UE Server 地址/端口、监听日志 | 本章启动顺序 |
| 连接进入却一直无 Pawn | TryStartPlayer 的双就绪条件 | Experience 与角色数据 |
| Pawn 出现但输入无效 | PawnExtension、IMC、InputConfig、UI 当前层 | 角色 GAS / UI 输入 |
| 退出后状态回退 | final save 与保存版本 | 网络与持久化 |

**截图阅读顺序**：客户端 A 图看 XP=25 和消耗后的 Mana；客户端 B 图看自己的 XP/Mana 保持独立；再看两个画面能观察到对方 Pawn。数值隔离、可见角色和后台保存需要各自证据，不能由一张 HUD 图全部推出。

本章命令需要多个独立终端/进程。先确认后端健康，再启动游戏服务器，再开客户端；退出时先让玩家离服并确认最终保存。保留自己的运行日志，历史 2026-09-13 报告不代表今天新修改的资产已经重新打包测试。
