## 三、打包与资产发现

在 Project Settings → Packaging 中将 `/TrainingRange/Maps/L_TrainingRange` 加入需要 Cook 的地图。检查 TrainingRange GameFeatureData 的 Experience 扫描和 Cook Rule。仅在编辑器内容浏览器中可见，不保证资产进入包。

使用项目的 Game/Client/Server Targets 构建所需平台。开发阶段先选择 Development，保留日志。若包中报找不到 Experience，检查 Primary Asset ID、插件是否进入构建、地图是否 Cook、软引用资产是否被规则收集。不要直接把整个项目目录作为 Additional Non-Asset Directory 打入包来规避扫描问题。

训练地图直接引用 `LyraExampleContent` 美术。`TrainingRange.uplugin` 必须同时声明 `ShooterCore` 与 `LyraExampleContent` 依赖；编辑器中偶然已经加载资源，不能代替插件依赖声明。配套脚本检查这两项依赖以及已保存的地图、Experience 和 GameFeatureData：

本教程的 Windows 构建选择 **D3D12 / Shader Model 6**，要求支持该渲染路径的显卡和驱动。官方配置同时包含 DX11 SM5、DX12 SM6 与 Vulkan SM6；训练包先不交付另外两条渲染路径。`examples/LyraTraining/Config/TutorialWindowsSM6.ini` 是原创增量配置，脚本把它追加到**实验副本**的 `Config/Windows/WindowsEngine.ini`，保留文件中原有 DPI、动态分辨率等设置：

```ini
[/Script/WindowsTargetPlatform.WindowsTargetSettings]
DefaultGraphicsRHI=DefaultGraphicsRHI_DX12
!TargetedRHIs=ClearArray
!D3D11TargetedShaderFormats=ClearArray
!D3D12TargetedShaderFormats=ClearArray
+D3D12TargetedShaderFormats=PCD3D_SM6
!VulkanTargetedShaderFormats=ClearArray
```

`!` 清空继承数组，`+` 再加入唯一目标；仅更改 Default Graphics RHI 不会从 Cook 列表删除其他 Shader Formats。需要交付 DX11 或 Vulkan 时，在自己的平台配置恢复对应格式，重新 Cook 并分别运行验证。此裁剪不修改官方分析基线。

源码引擎首次打包还要准备两个 **Engine Program** 目标。`UnrealPak Win64 Development` 提供 Pak/IoStore 工具；`BootstrapPackagedGame Win64 Shipping` 提供 Windows 归档顶层的启动程序模板。它们不是训练场插件，也不是 `LyraEditor` 构建产物。保存并正常关闭使用同一引擎的编辑器，等待其他 UBT 构建结束，再在 PowerShell 中依次执行：

```powershell title="源码引擎的 Windows 打包工具"
& E:/UnrealEngine/Engine/Build/BatchFiles/Build.bat `
  UnrealPak Win64 Development `
  -WaitMutex -NoHotReloadFromIDE -NoUBA -MaxParallelActions=3
if ($LASTEXITCODE -ne 0) { throw 'UnrealPak 构建失败，先处理构建日志。' }

& E:/UnrealEngine/Engine/Build/BatchFiles/Build.bat `
  BootstrapPackagedGame Win64 Shipping `
  -WaitMutex -NoHotReloadFromIDE -NoUBA -MaxParallelActions=3
if ($LASTEXITCODE -ne 0) { throw 'Windows Bootstrap 构建失败，先处理构建日志。' }
```

每次确认 `Result: Succeeded`，再核对 `E:/UnrealEngine/Engine/Binaries/Win64/UnrealPak.exe` 与 `BootstrapPackagedGame-Win64-Shipping.exe` 存在。`package-training.ps1` 的 Package 分支会先检查这两个文件；缺失时停止并打印对应的显式构建命令。两条命令不传 `-Project`，同一引擎下的实验工程可复用这些工具；引擎源码或配置变化后仍需由 UBT 核对是否过期。

本机 5.8.1 的 `BuildProjectCommand.Automation.cs` 在 source engine 的 `-build` 阶段还会核对这两个工具目标，`-skipbuildeditor` 只跳过 Editor。先按上面的命令完成首次工具构建，能把这一阶段的并行度也明确限制为 3。UAT 的 `-ubtargs` 传给 cooked 游戏目标，不是所有 Engine Program 的统一限流参数。`WinPlatform.Automation.cs::StageBootstrapExecutable` 使用上面的 Shipping 模板创建顶层启动程序；验收脚本则直接运行归档内的 `Binaries/Win64/LyraGame.exe`，报告会记录实际进程路径。

```powershell
# 只显示将执行的参数，不启动 UAT、UBT 或 Cook。
./scripts/package-training.ps1 -Mode Package -ShowCommand

# 先完成完整 Editor 构建并正常关闭编辑器。
# Cook 模式使用已有 Editor，不构建游戏可执行文件。
./scripts/package-training.ps1 -Mode Cook

# 构建 LyraGame Development，Cook、Stage、Pak/IoStore 并归档。
./scripts/package-training.ps1 -Mode Package
```

脚本显式指定 `/TrainingRange/Maps/L_TrainingRange`，不依赖默认前端地图。默认产物位于 `LyraDocLabs/Artifacts/LyraTraining` 的本次唯一目录，日志与退出码记录到 `verification/training-cook.json` 或 `training-package.json`，各次目录还保留自己的 `report.json`。`Package` 模式会调用 UBT，需与其他共享引擎的构建错开；脚本发现同引擎编辑器、Live Coding 或 UBT 进程时会停止并列出 PID，不自动关闭进程。`Cook` 模式只要求训练工程编辑器关闭且没有同引擎 Live Coding，不会因另一个项目的 C++ 构建而拒绝执行。

Cook 直接调用已有 `UnrealEditor-Cmd.exe -run=Cook -TargetPlatform=Windows`，不通过 UAT。`-Multiprocess` 在本机 `TargetPlatformManagerModule.cpp` 跳过自动 SDK 验证的 UBT 启动；它与 `-CookProcessCount=1` 同时使用，日志明确显示 Cook 自身仍为单进程。`-corelimit=3` 配合 Shaders INI 覆盖，把本机 `ShaderCompiler.cpp` 的低核心分支限制为 2 个 ShaderCompileWorker，减少与其他任务同时运行时的内存压力。

`Package` 分支也通过 UAT 的 `-AdditionalCookerOptions` 传递同一套单进程 Cook、3 个可用核心与 2 个 SCW 参数；通过 `-ubtargs=-NoUBA -MaxParallelActions=3` 禁用 LyraGame 构建的 UBA，并把该游戏目标限制为最多 3 个并行动作。工具目标先按前面的独立命令完成构建。这两个限制分别控制 C++ 构建与 Shader 编译，不能只设置其中一个。脚本记录实际 worker 日志，若出现超过 2 个本地 worker 则报告失败；缓存完全命中时，参数记录与原生日志仍保留供核查。

打包前还需已构建的 `Engine/Binaries/DotNET/AutomationTool/AutomationTool.dll` 和 `AutomationUtils/net10.0/AutomationUtils.Automation.dll`，以及本机可用的 Windows SDK。脚本先检查这两个工具文件，并传入本机 UAT 原生支持的 `-NoCompileUAT -NoCompile -NoAutoSDK`，避免打包时隐式重编译 UAT/脚本模块或启动 AutoSDK 安装。它们不跳过下面的 LyraGame C++ 构建、Cook、Shader 编译、Stage 或归档。若工具缺失，先正常关闭共享引擎的编辑器、等待其他构建结束，再单独执行 `E:/UnrealEngine/Engine/Build/BatchFiles/RunUAT.bat -CompileOnly` 完成源引擎 AutomationTool 和脚本模块前置构建，确认退出码为 0 后重试。该准备命令允许构建工具自身，不能与教程中的禁止重编译参数组合使用。

若本机使用 HTTP 代理，UAT 的本地 Zen 就绪检查也可能受到影响。本机 5.8.1 的 `ZenUtils.cs::CreateHttpClientInternal` 使用默认 .NET `HttpClient`；实测只有 `NO_PROXY=...::1` 时，对 `http://[::1]:8558` 仍可能走代理并收到 502，而 Zen 本身已经正常提供 Cook 内容。Package 调用会临时在当前进程的 `NO_PROXY` 保留已有条目并加入 `localhost`、`127.0.0.1`、`::1`、`[::1]`，让 UAT 子进程直接连接本地服务；成功或异常结束都在 `finally` 恢复原值。脚本不修改系统代理，不输出代理地址或凭据，也不因为这个连接问题更换 Cook 存储方式。遇到 Zen 超时时，应先区分实际服务未就绪与代理误路由，不要立即重做全部 Cook。

**单独的 Cook 模式**使用 `-SkipZenStore`，把 Cook 后的地图和资产包写入独立目录，便于检查真实文件；**Package 模式**沿用 UAT 的 Zen Cook/Stage 流程，再生成 Pak/IoStore 与归档。两种模式均用 MCP 的 `EditorPerProjectUserSettings` 命令行覆盖关闭本次自动服务启动，避免占用另一个编辑器的 8000 端口。进程参数只作用于该命令，渲染路径增量保存在实验副本，官方项目配置保持原样。Cook 会继续遵守 Asset Manager 的 Always Cook 和依赖规则，指定一张地图不代表只处理该地图文件。

参数已按本机 5.8.1 `CookCommandlet.cpp`、`TargetPlatformManagerModule.cpp`、`ShaderCompiler.cpp` 以及 UAT 的 `ProjectParams.cs`、`BuildProjectCommand.Automation.cs` 核对；运行结果以验证目录实际报告为准。UAT 成功后还要启动归档内可执行文件，传入训练地图路径，并重新检查 Experience、输入、HUD 和武器。本次已完成下文的 Package 与两次归档运行验收。`training-package.json` 的 `runtimeVerification: pending` 是 **UAT 结束时**的快照；实际后续结果在独立的 `training-package-runtime*.json`，其中保存了该包报告的 SHA256。保留包报告原字节，避免事后修改使来源哈希失配。

### 归档程序的原生运行验收

新增的原创源码位于 `examples/LyraTraining/Plugins/GameFeatures/TrainingRange/Source/TrainingRangeVerification`。先把插件 `.uplugin` 和 `Source` 一起复制到训练实验工程，再构建完整 Editor 目标；完成并保存最新导航地图后执行上面的 `-Mode Package`。脚本会检查实验工程的验收源码与文档仓库一致，并记录本次地图、插件描述和验收源码 SHA256。

使用 PowerShell 7.2 或更新版本，在文档仓库执行：

```powershell

# 运行实际归档内 Binaries/Win64/LyraGame.exe。
```
