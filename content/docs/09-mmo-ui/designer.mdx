## 学习目标与前置条件

本篇把界面的布局、颜色、字体、间距和固定文案全部放进可编辑资产。C++ 父类保留登录请求、按钮业务、CommonUI 激活/焦点、UIExtension 和 ViewModel 生命周期；游戏运行时不调用 `ConstructWidget` 拼装画面。

先完成 MMORPGEditor 构建并启用 CommonUI、Model View ViewModel 和教学 Editor 工具。实际资产契约是 `examples/MMORPG/ui-designer-contract.json`；固定文案契约是 `ui-designer-strings.json`。所有控件名称区分大小写，下面的名字直接对应 C++ `BindWidget` 或真实 MVVM 绑定，不能为了显示中文而重命名它们。

资产生成器 `prepare_content.py` 在 Editor 中执行与本篇等价的写资产操作，便于复现和检查；它不是游戏运行时的 UI 实现。已有资产可以直接打开 Designer 修改。再次执行生成器会按教学定义重建这些资产的 WidgetTree，因此保留自己的布局改动时应先复制到独立实验目录。

## 一、先建立字符串表

1. Content Browser 中建立 `/Game/Localization` 目录，在创建资产菜单搜索 **String Table**；本机版本属于 Data 分类。命名为 `ST_MMO`。
2. 双击字符串表，将 Namespace 设为 `MMOUI`。
3. 按 `ui-designer-strings.json` 的 `entries` 逐项添加 Key 和 Source String。Source 使用英文，Key 保持稳定；例如 `Login.Title` → `Begin your journey`、`Action.SignIn` → `Sign in`、`Language.Chinese` → `Simplified Chinese`。
4. 保存字符串表。完整对象路径为 `/Game/Localization/ST_MMO.ST_MMO`。
5. 后面编辑 TextBlock.Text、EditableTextBox.Hint Text 时，打开文本字段的本地化/字符串表选择器，选择 ST_MMO 再选择 Key。不要把中文直接写成不参与收集的运行时字符串。

| 文案位置 | 字符串表 Key 示例 | 中文翻译 |
| --- | --- | --- |
| 登录标题 | `Login.Title` | 开启旅程 |
| 账号标签与提示 | `Account.Username`、`Account.UsernameHint` | 账号名称；3–32 位字母、数字或下划线 |
| 密码提示 | `Account.PasswordHint` | 12–128 个字符 |
| 登录 / 注册 | `Action.SignIn`、`Action.Register` | 登录 / 注册账号 |
| 进入世界 | `Action.Enter` | 进入世界 |
| 背包 / 设置 | `Action.Inventory`、`Action.Settings` | 背包 / 设置 |
| 语言按钮 | `Language.Chinese`、`Language.English` | 简体中文 / English |
| 退出确认 | `Confirm.Accept`、`Confirm.Cancel` | 保存并退出 / 继续游戏 |

45 条固定文案都在同一份表中维护。中文属于 `zh-Hans` 翻译，原生文化为 `en`；切换文化会让表引用重新求值。角色名称和账号输入是用户数据，不能拿它们当字符串表 Key。等级、法力、冷却等动态文案由 ViewModel 的 `FText` 格式化后通过 FieldNotify 更新。

## 二、创建七个 Widget Blueprint，并选对父类

在 `/Game/UI` 的创建菜单选择 **User Interface → Widget Blueprint**，在父类选择中展开 All Classes，按下表选择。创建后打开 **Designer**，不要先在空树上 Compile：带必需 `BindWidget` 的父类会在控件缺失时报告错误。先放齐控件并命名，再编译。

| 资产名称 | 原生父类 | 用途 |
| --- | --- | --- |
| `WBP_MMOLayout` | `MMORootLayout` | Game/Menu/Modal 三层容器 |
| `WBP_Login` | `MMOLoginPanel` | 账号表单和角色创建/选择 |
| `WBP_ManaStatus` | `UserWidget` | 可复用的法力文本与进度条 |
| `WBP_PlayerHUD` | `MMOHUDPanel` | 玩家状态、目标、技能与菜单入口 |
| `WBP_Inventory` | `MMOInventoryPanel` | 背包内容与药剂操作 |
| `WBP_Settings` | `MMOSettingsPanel` | 画质、语言、退出入口 |
| `WBP_Confirm` | `MMOConfirmPanel` | 退出确认模态框 |

如果已经有同名蓝图，打开 Class Settings 核对 Parent Class。Native Parent 不负责 WidgetTree，Designer 中的布局就是最终布局。`WBP_ManaStatus` 要先编译保存，随后才能从 Palette 搜索并放进 HUD。

## 三、建立根布局的 CommonUI 三层

1. 打开 `WBP_MMOLayout` 的 Designer。如果模板有 Canvas Panel，选中并删除。
2. 从 Palette 拖入 **Overlay** 作为根，命名 `LayerLayout`，Visibility 选择 **Not Hit-Testable (Self Only)**。
3. 依次向 Overlay 放入三个 **Common Activatable Widget Stack**，命名 `GameLayer`、`MenuLayer`、`ModalLayer`，全部勾选 Is Variable。
4. 选中每个 Stack，在 Overlay Slot 中把 Horizontal/Vertical Alignment 都设为 Fill，Padding 为 0。顺序决定叠放层级：Game 在底部，Modal 在顶部。
5. 教学资产保存的 Stack **Transition Duration = `0.16`**，但这不是本项目运行时的转场时长：下一步注册层时，所复用的 `UPrimaryGameLayout::RegisterLayer` 会将它设为 **`0.0`**，以保留 Lyra 的手柄焦点行为。因此只修改 Designer 的这个字段不会改变游戏内切换效果。需要淡入淡出时先用页面内部的 UMG Animation，再单独验证返回、快速开关与焦点；不要在角色 Tick 中更新界面透明度。
6. Compile，确认没有缺少 GameLayer/MenuLayer/ModalLayer 的错误，再 Save。

```text
LayerLayout (Overlay)
├─ GameLayer  (CommonActivatableWidgetStack)
├─ MenuLayer  (CommonActivatableWidgetStack)
└─ ModalLayer (CommonActivatableWidgetStack)
```

`UMMORootLayout::NativeOnInitialized` 只把这三个已存在的容器注册到 `UI.Layer.Game`、`UI.Layer.Menu`、`UI.Layer.Modal`。构造、停用与返回仍使用 CommonUI 生命周期；Root 不手工 AddToViewport 每个弹窗。


![WBP_MMOLayout：三个真实 CommonUI Stack 的 Overlay Slot 水平垂直 Fill](/media/configuration/mmorpg/designer-root-stacks-fill.png)

图：按住 Ctrl 多选 GameLayer、MenuLayer、ModalLayer 后的共同属性。空容器尚未 Push 页面时可显示 Collapsed；运行时由 CommonUI 根据页面激活状态处理可见性，不用在 Tick 中强制 Visible。

![根布局 Stack 在 Designer 中保存 Fade Only 和 0.16 Transition Duration](/media/configuration/mmorpg/designer-root-stacks-transition.png)

图：这张配置图显示资产值 `0.16`。本项目所复用的 CommonGame `RegisterLayer` 在运行时将其覆盖为 `0`，详见 `verification/mmorpg-layer-transition-review.json`；图片不代表游戏里实际播放了 0.16 秒转场。

## 四、统一面板布局和样式

Login、Inventory、Settings、Confirm 使用相同层次，HUD 使用左上对齐版本。先把每个资产的共同结构建好，再放业务控件：

1. 根用 Overlay，名为 `ScreenLayout`，Visibility 选 Self Only 不参与命中。
2. 在根中放 SizeBox `PanelWidth`，Overlay Slot Padding=`24`；普通面板居中，HUD 选择 Left/Top。
3. SizeBox 内放 Border `PanelBackground`，Padding=`24`，Brush Color 使用不透明深蓝；再把 VerticalBox 放入 Border。
4. Login 的 VerticalBox 必须叫 `Form`；其他分别叫 `HUDLayout`、`InventoryLayout`、`SettingsLayout`、`ConfirmLayout`。
5. 每个业务控件在父 VerticalBox Slot 中水平 Fill、底部 Padding 默认 `12`；标签与输入框之间可用 `5`，同一行按钮的 HorizontalBox Slot 使用 Fill，按钮间距 `10`。

| 属性 | 教学默认值 | 编辑位置 |
| --- | --- | --- |
| PanelWidth | Login `680`；HUD `540`；其他 `600` | SizeBox → Width Override |
| 面板色（线性 RGBA） | `(0.035, 0.052, 0.09, 1)` | Border → Brush Color |
| 正文色 | `(0.90, 0.94, 1, 1)` | TextBlock → Color and Opacity |
| 次要文字色 | `(0.62, 0.73, 0.87, 1)` | TextBlock → Color and Opacity |
| 字体 | 正文 `18`，分区 `22`，标题 `28–30` | TextBlock → Font → Size |
| 文本换行 | Auto Wrap Text=true | TextBlock → Wrapping |
| 输入行最小高度 | `44` | 包裹输入框的 SizeBox → Min Desired Height |
| 按钮行最小高度 | `46` | 包裹 Button 的 SizeBox → Min Desired Height |
| 法力/生命进度条高度 | `14` | 包裹 ProgressBar 的 SizeBox |

按钮内部放 TextBlock，文案引用 ST_MMO。选中这个 TextBlock，在 **Slot (Button Slot) → Horizontal Alignment** 选择 **Fill**，再把 TextBlock 的 **Justification** 设为 **Center**，保留 Auto Wrap Text。Fill 让文本取得按钮实际可用宽度，Center 负责文字居中；只把 Slot 设为 Center 会把文本限制在期望尺寸，切换文化后可能出现宽按钮中的额外换行。HUD 的窄动作按钮仍可按实际宽度合理换行。


![登录按钮的子 TextBlock：Button Slot 水平 Fill、垂直 Center](/media/configuration/mmorpg/designer-button-label-slot.png)

图：选中的是 `LoginButtonLabel` 子控件，其 Details 展示 Button Slot。先让 Slot 分配实际宽度，再由 TextBlock Justification 居中文字；不要把 Button 自己的 HorizontalBox Slot 和这里的 Button Slot 混淆。

Button 的 Normal/Hovered/Pressed 样式都在 Designer 的 Style 中编辑。输入框用浅色背景、深色文字，提示与标签分开，避免密码输入后读者看不出哪个字段是什么。没有为每个控件添加 Canvas Slot，也没有 RetainerBox、循环动画或每帧绑定函数。

## 六、制作可复用法力控件和真实 MVVM 绑定

先做 `WBP_ManaStatus`：

1. 根为 VerticalBox `ManaLayout`。
2. 第一行 TextBlock 命名 `ManaText`、Is Variable=true，18 pt，初始文本引用 `Mana.Preview`。
3. 下一行 SizeBox `ManaBarSize` 高度 14，里面放 ProgressBar `ManaBar`、Is Variable=true，Percent 默认 1，Fill Color 使用蓝色。
4. 在 Widget Blueprint 的 **Window → Viewmodels** 添加 `MMOPlayerViewModel`，实例名必须为 `PlayerVM`。选中这个来源，把 Creation Type 设为 **Manual**，允许它在运行时注入。
5. 打开 **Window → View Bindings**，添加 `PlayerVM.ManaLabel → ManaText.Text` 和 `PlayerVM.ManaFraction → ManaBar.Percent`。
6. 两条都设为 **One Way to Destination**，Execution Mode 覆盖为 **Immediate**。不要使用每 Tick 的 UMG 函数绑定，也不要把 ManaText.Text 反向写回服务器属性。
7. Compile、Save；View Bindings 中不应有红色字段或找不到来源的错误。


![WBP_ManaStatus 的完整 Designer 层级：ManaLayout、ManaText、ManaBarSize、ManaBar](/media/configuration/mmorpg/designer-mana-layout.png)

图：父类为 UserWidget。左侧 ManaBarSize 已展开，里面是唯一的 ManaBar；Designer 预览宽度来自所选预览画布，运行大小由 HUD 的嵌套 Slot 约束。

![ManaStatus 的 PlayerVM 来源：MMOPlayerViewModel，Creation Type Manual](/media/configuration/mmorpg/mvvm-mana-source.png)

图：Window → Viewmodels 打开后，点击已有 PlayerVM 行；来源属性会显示在主 Widget Blueprint 的 Details 中。工具栏 Add 用于新增来源，不能用它核对已有来源。

![ManaStatus 的两条真实 View Bindings，ManaLabel 到 Text、ManaFraction 到 Percent](/media/configuration/mmorpg/mvvm-mana-bindings.png)

图：Window → View Bindings 打开底部面板。两条均启用、单向到目标，Execution Mode 为 Immediate；不是普通 UMG 的每帧 getter 绑定。

Manual 表示 Widget 不创建一个与游戏状态无关的新 ViewModel。HUD 的父类在收到玩家上下文后，分别给 HUD 和嵌套 `ManaStatus` 注入**同一个** PlayerVM；断开或销毁时清除引用。

## 七、制作 HUD、目标与技能快捷入口

该轮中文 HUD 使用 `/Game/UI/WBP_PlayerHUD`，其中 `ManaStatus` 是独立 `/Game/UI/WBP_ManaStatus` 的实例。玩家 A 为经验 25、法力 40；画面来自 2026-09-13 19:27–19:28 UTC 的实际打包渲染回归，1920×1080、中等画质。右侧 Manny 的动画配置见[角色动画章节](/docs/08-mmorpg/animation)。

打开 `WBP_PlayerHUD`，按第四节建立左上面板，在 `HUDLayout` 放置：

| 控件 | 名称 | 内容或用途 |
| --- | --- | --- |
| TextBlock | `Title` | `HUD.Title` |
| TextBlock | `Values` | 玩家等级、经验与状态，随后绑定 StatusText |

| HorizontalBox | `MenuActions` | `InventoryButton`、`SettingsButton` |

![HUD Designer 层级与实际嵌套 WBP_ManaStatus 控件](/media/configuration/mmorpg/designer-hud-layout.png)

图：在 Hierarchy 选中 ManaStatus，确认它是可复用的 WBP_ManaStatus 实例；目标栏、技能按钮、菜单按钮和输入提示仍可以直接在 Designer 修改布局。

## 八、制作背包、设置与模态确认

三个资产都使用第四节的居中面板。按下面控件表完成后再 Compile、Save。

| 资产 | 必须存在的变量控件 | 文案与绑定 |
| --- | --- | --- |

## 十、生成、编译与验收

已构建含 Editor bridge 的 MMORPGEditor 后，可以在编辑器 **Tools → Execute Python Script** 选择实验根的 `prepare_content.py`。完整脚本先验证动画和角色默认值，再配置 Experience 数据；UI 部分的顺序为 ST_MMO → 七个 Designer 资产 → UI Policy。WBP_ManaStatus 在 HUD 之前编译，必需控件在 Compile 之前全部写入。

生成记录在实验工程 `Saved/Evidence/ui-designer-assets.json`，每个 WBP 另有 `WBP_…-designer.json`，记录控件类/名称/IsVariable、Canvas 数量、真实绑定数量和编译错误/警告。`saved=true` 与 `gameplayExecuted=false` 分别说明保存完成和该步骤尚未运行游戏，不能混为运行通过。

遇到 `field ... exists but not accessible at runtime`，先区分两层配置：Designer 的 **Is Variable** 使控件可以被查找；C++ 中已声明的同名 BindWidget 属性还需要允许蓝图读取，MVVM 才能编译到目标控件的字段路径。例如 HUD 的 Values 声明如下，Text 的赋值仍由真实 View Binding 完成：

```cpp title="MMOUI.h：供 MVVM 访问的 BindWidget 控件引用"
UPROPERTY(BlueprintReadOnly, meta=(BindWidget, AllowPrivateAccess="true"))
TObjectPtr<UTextBlock> Values;
```

仅改 WBP 的 Is Variable 不能替代原生属性的访问权限。修改头文件后正常关闭编辑器，重新构建 Editor，再打开 WBP 编译。首次加载早期空 WBP 时出现缺 BindWidget 错误，也应先填齐 Designer 并保存，再重开验证；不能把加载旧资产时的失败日志当成本次新树已编译成功。
