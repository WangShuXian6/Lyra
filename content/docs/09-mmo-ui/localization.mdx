## 学习目标与前置条件

本篇为 MMORPG 游戏提供 **简体中文 `zh-Hans` 和英文 `en`**。固定标签、登录反馈、错误提示、角色状态、药剂数量和冷却文案都能切换语言，账号和角色名称保持玩家输入的原文。

先完成 [Designer 与 MVVM 工作流](/docs/09-mmo-ui/blueprint-workflow)，编译 `MMORPGEditor`，运行 `prepare_content.py` 并保存所有 UI 资产。对应 UE 5.8.1，源码核对日期 **2026-09-13**。资源编译和运行验证是两个检查点，不能用 PO 已生成代替游戏内验收。

## 确定文字的归属

| 内容 | 保存位置 | 修改入口 |
| --- | --- | --- |
| 固定标签与账号、密码等输入框占位提示 | `/Game/Localization/ST_MMO` | String Table 编辑器 |
| 请求中、错误码提示、状态格式、动态键鼠/手柄 InputHint | `Source/MMORPG/Private/MMOUI.cpp` | `LOCTEXT`，namespace 为 `MMOUI` |
| GameInstance 网络与准入失败提示 | `Source/MMORPG/Private/MMOGameplay.cpp` | `NSLOCTEXT`，namespace 为 `MMOUI` |
| 玩家输入的角色名 | 后端与 PlayerState | 作为文化无关的用户内容展示 |
| 中英文翻译资源 | `Content/Localization/MMO` | Dashboard 或命令行流水线 |
| 当前语言偏好 | 游戏 `Saved/Config/.../GameUserSettings.ini` | Settings 语言按钮 |

固定标签共享字符串表条目。业务代码与 ViewModel 显示属性使用 `FText`，控件直接接收它，避免先 `ToString()` 再拼成另一段文字。字符串表引用保留文字身份，翻译资源根据 namespace、key 和原文匹配。参见 [Epic 字符串表说明](https://dev.epicgames.com/documentation/unreal-engine/using-string-tables-for-text-in-unreal-engine?lang=en-US)。

## 创建字符串表并在 Designer 引用

1. 在 Content Browser 的 Content 下新建 `Localization` 文件夹。
2. 在文件夹右键，在创建菜单搜索 **String Table**，命名 `ST_MMO`。UE 5.8.1 的资产分类为 Data；运行过生成脚本则打开现有表。
3. 双击打开，设置 **Namespace = MMOUI**。
4. 添加条目：**Key = Settings.Title**，**Source String = Settings**。另加 `Action.Back` / `Back` 和 `Settings.Language` / `Language`。
5. 按相同步骤输入 `examples/MMORPG/ui-designer-strings.json` 的其余 key / source 条目并保存。英文是源语言，清单中的中文稍后作为翻译导入。
6. 打开 `/Game/UI/WBP_Settings`，切换到 **Designer**，在 Hierarchy 选择标题 Text Block。
7. 在 Details 的 **Text** 属性旁展开文本高级选项，选择 **String Table** 引用，表选 `ST_MMO`，Key 选 `Settings.Title`。
8. 选择返回按钮里的 Text Block，绑定 `Action.Back`；语言标题绑定 `Settings.Language`。不要只把预览文字手改成中文。
9. 编译并保存 WBP，重新展开 Text 属性，确认保留表与 Key 引用。

教学生成器创建 `UStringTable`、写入 Key，再把 `FText::FromStringTable` 存进真实 WBP。布局和引用仍可在编辑器修改。重新运行生成器会恢复教学布局，自己的视觉改动应在复制出的 WBP 中进行。

~~~cpp title="等价的文字引用；布局仍在 Widget Blueprint 中"
const FText Title = FText::FromStringTable(
    TEXT("/Game/Localization/ST_MMO.ST_MMO"),
    TEXT("Settings.Title"));
~~~

## 让业务文案可收集、数值可格式化

`MMOUI.cpp` 在文件作用域声明 namespace，末尾取消宏。下面把法力格式化和角色名转换放在一起说明，两者来自不同的刷新分支，并非完整函数。`Mana` 是当前数值；使用 `State->GetPlayerName()` 前，调用分支必须已确认 State 非空。状态格式由 `LOCTEXT` 定义，参数按自己的语义转成 `FText`：

~~~cpp title="FText 格式化片段；在相应 ViewModel 刷新函数中使用"
#define LOCTEXT_NAMESPACE "MMOUI"
const FText Label = FText::Format(
    LOCTEXT("ManaValue", "Mana {0} / 100"),
    FText::AsNumber(FMath::RoundToInt(Mana)));
const FText PlayerName = FText::AsCultureInvariant(State->GetPlayerName());
#undef LOCTEXT_NAMESPACE
~~~

保留 `{0}` 等参数，翻译可以调整其位置。冷却用 `FNumberFormattingOptions` 固定一位小数；数量、等级、经验用 `FText::AsNumber`。不要用 `FString::Printf` 预先生成整句，也不要直接展示服务器英文错误详情。客户端根据 `error.code` 选择本地文案，未知错误使用可翻译的通用提示。

生命、法力、进度、背包与目标分别由属性委托或复制通知更新。冷却计时只更新冷却字段，归零时停止；切换文化时刷新显示字段一次，无需重新创建 CommonUI 层栈。

## 在 Localization Dashboard 配置目标

1. 保存 WBP 和 `ST_MMO`，打开 **Tools → Localization Dashboard**。
2. 使用已有目标 **MMO**。从自己的空白工程操作时，点击新增目标，名称填 MMO。
3. 将 **Loading Policy** 设为 **Game**。
4. 在 Cultures 添加 **English (en)**、**Chinese (Simplified, zh-Hans)**，将 English 设为 Native Culture。
5. 启用 **Gather from Text Files**，搜索目录填 `Source/MMORPG`、`Plugins/MMOFramework/Source`，扩展名填 h、cpp，关闭 Editor Only 数据。
6. 启用 **Gather from Packages**，包含路径填 `Content/UI/*`、`Content/Localization/ST_MMO.uasset`，扩展名填 uasset，关闭 Editor Only 数据。
7. 保存设置，点击 **Gather Text**，等待完成，确认日志无错误且字数大于零。
8. 点击 **Export Text**，导出 UE PO 格式；英文和中文各有一个 MMO.po。
9. 打开 `Content/Localization/MMO/zh-Hans/MMO.po`，保持 msgctxt、msgid 不变，在 msgstr 填中文，保存为 UTF-8。
10. 回 Dashboard 点击 **Import Text**，再点 **Compile Text**。
11. 检查 en/MMO.locres、zh-Hans/MMO.locres 与 MMO.locmeta 已生成。
12. 在 **MMO 目标**内点击 **Count Words**，等待原生命令完成，查看 en、zh-Hans 的实际词数与完成比例。它读取现有 manifest 和 archive，更新 `Content/Localization/MMO/MMO.csv`，不会重新收集或修改译文。
13. 比较两种语言的已翻译词数与源词数；本教程完整翻译时应相等、完成比例为 100%。这里统计的是有翻译的**英文源词数**，不是中文字符数，也不是 84 个文案 key 的数量。

目标配置在 `Config/DefaultEditor.ini`，命令行配置在 `Config/Localization/MMO_Gather.ini`、`MMO_Export.ini`、`MMO_Import.ini`、`MMO_Compile.ini`、`MMO_GenerateReports.ini`。修改目标后提交配置与翻译，不应只保留某台电脑的 Saved 内容。[Epic 本地化工具流程](https://dev.epicgames.com/documentation/en-us/unreal-engine/localization-tools-in-unreal-engine)说明了 Dashboard 与这些操作的关系。

Dashboard 字数为 0 时，先检查 `MMO.csv` 是否存在。冲突标记 **Unknown** 表示没有 `MMO_Conflicts.txt`，不能据此认定发生冲突；原生报告为空文件时才显示 Clear。若报告非空，打开它定位相同 namespace/key 对应的不同原文，修正来源后重新 Gather。不要手写空文件来清除标记。

~~~text title="PO：原文和 key 不改，只翻译 msgstr"
msgctxt "MMOUI,Settings.Title"
msgid "Settings"
msgstr "设置"
~~~

## 用脚本重现收集、翻译与编译

这个入口需要系统终端可调用的 **Python 3**，本机验证版本为 3.13.11。`Build-Localization.ps1` 的 Translate 阶段直接执行 `python translate-localization.py`，只使用 Python 标准库，无需 pip 安装依赖。UE 的 Python Editor Script Plugin 用于编辑器内资产操作；启用它不会自动把系统 `python` 命令加入 PATH。

1. 尚未安装时，从 [Python 官方 Windows 下载页](https://www.python.org/downloads/windows/)安装 Python 3 的 Windows 64 位版本。使用标准安装器时勾选 **Add Python to PATH**；已安装但漏选，可重新运行安装器选择 Modify 并启用该项，或把实际安装目录加入用户 PATH。入口说明见 [Python Windows 安装文档](https://docs.python.org/3.13/using/windows.html#finding-the-python-executable)。
2. 安装或修改 PATH 后重新打开 **PowerShell 7**，执行下面检查。预期第一条返回实际解释器或版本管理器的路径，第二条输出 `Python 3.x.x`，第三条输出同一 Python 3 的实际可执行文件路径。

~~~powershell
Get-Command python | Select-Object Source
python --version
python -c "import sys; assert sys.version_info.major == 3; print(sys.executable)"
~~~

若 `python` 不存在或只打开 Microsoft Store，先修复安装目录的 PATH 或 Windows 的 Python 应用执行别名，再重复检查。仅有 `py` 启动器可用还不满足当前脚本的 `python` 命令要求。

保存工作并正常关闭 MMORPG 编辑器，在 PowerShell 执行：

~~~powershell
Set-Location F:/UE/LyraDoc
pwsh -File scripts/mmorpg/Build-Localization.ps1 -Project F:/UE/LyraDocLabs/MMORPG/MMORPG.uproject -Engine E:/UnrealEngine
~~~

脚本依次执行 Gather → Export → Translate → Import → Compile → GenerateReports。Translate 只填写 UE 已导出的 PO，不自行生成收集清单。固定译文来自 `ui-designer-strings.json`，业务译文来自 `localization-runtime-zh-Hans.json`。

`MMO_Gather.ini` 的最后一步在**同一 Gather 进程**中生成 `MMO_Conflicts.txt`，保留本轮源码和资产收集得到的冲突上下文；脚本遇到非空报告即停止。最终 GenerateReports 只读取导入后的 archive，生成 Dashboard 的真实 `MMO.csv`，并核对 en、zh-Hans 的词数均覆盖源词数。结果 JSON 分别记录 `translation` 中的 key 数、`wordCounts` 中的原生词数和 `conflicts.count`，三者含义不同。

只更新现有译文的统计时，保存并正常关闭编辑器后可以单独执行下面命令；它不会更新 Gather 冲突结论。之后重新打开 Dashboard 查看统计。

~~~powershell
& E:/UnrealEngine/Engine/Binaries/Win64/UnrealEditor-Cmd.exe F:/UE/LyraDocLabs/MMORPG/MMORPG.uproject -run=GatherText -config=Config/Localization/MMO_GenerateReports.ini -unattended -nop4 -NullRHI -Multiprocess
~~~

业务清单中的每个 key 同时保存已审核的英文 `source` 和 `zh-Hans`。脚本先检查 C++ 的 LOCTEXT / NSLOCTEXT 原文与这份 source 一致，再比较 UE PO 的 msgid；英文修改后必须重新核对中文并一起更新清单，不能仅凭相同 key 沿用旧译文。输入提示包含游戏动作与菜单入口：键鼠 I / P、手柄 View / Menu 分别打开背包和设置，Escape / B 用于菜单返回。

新增 LOCTEXT 没有译文、Key 对不上、原文变化或格式参数缺失都会中止流程。修正后从 Gather 重新执行。日志在实验项目 `Saved/Logs/Localization/<时间>`，结果与产物 SHA-256 写入 `verification/mmorpg-localization.json`。

**2026-09-13 / UE 5.8.1 实测：** 16:35:34–16:36:37 UTC 依次完成 Gather、Export、Import、Compile、GenerateReports，五个原生进程退出码均为 0。中间严格翻译步骤核对了 **84 条文案（45 条 Designer、39 条业务）**，包含死亡提示 `MMOUI.PlayerDead`。同一 Gather 进程生成的 `MMO_Conflicts.txt` 为 0 字节、冲突组数为 0；最终 `MMO.csv` 中 Source、en、zh-Hans 的源词覆盖数均为 **404**。404 是原生词数，84 是稳定文案标识数量。

英文与中文 archive、PO、locres，以及 MMO.manifest、MMO.locmeta、MMO.csv、MMO_Conflicts.txt 共 **10 个原创产物**已同步到 `examples/MMORPG/Content/Localization/MMO`。复制后逐文件核对字节与 SHA-256，并把中文 PO 的全部 84 项 identity/原文/译文再次与审核清单对照。来源和原生产物哈希见 `source-evidence/mmorpg-localization.json`，完整步骤结果见 `verification/mmorpg-localization.json`。

这份结果证明实际收集、译文覆盖、导入和资源编译。游戏内程序触发的切换、新进程偏好恢复以及打包 Client 中的资源可用性，已由下节的实际 Stage 与打包运行报告分别验证；这些运行结论不由资源编译结果推断。

## 配置加载路径、字体和打包

1. 打开 **Project Settings → Packaging**。
2. 将 **Internationalization Support** 设为 **EFIGSCJK**，提供英文与中日韩所需 ICU 数据。
3. 在 **Localizations to Package** 仅选 en 和 zh-Hans。这与 ICU 支持范围不同，此处决定打包本项目的哪些翻译。
4. 在 **Additional Asset Directories to Cook** 加 `/Game/Localization`，保留已有 /Game/UI 和 /MMOCore。
5. 保存设置，检查 **DefaultGame.ini** 的 `[Internationalization]` 包含 `+LocalizationPaths=%GAMEDIR%Content/Localization/MMO`。这是 Game 配置域，不能放进 DefaultEngine.ini 代替。
6. 编译翻译后再执行 Client Cook/Stage；在暂存目录或 Pak 清单中检查两种文化的 locres 与 locmeta。

![Packaging 的 Internationalization Support 为 EFIGSCJK](/media/configuration/mmorpg/project-packaging-internationalization.png)

图：Project Settings → Packaging，搜索国际化支持字段。该值选择 ICU 数据范围，不等于勾选所有项目翻译文化。

![Localizations to Package 展开语言列表：English 勾选](/media/configuration/mmorpg/project-packaging-english.png)

![同一 Localizations to Package 列表：Chinese Simplified zh-Hans 勾选](/media/configuration/mmorpg/project-packaging-chinese.png)

图组：同一原生列表先显示 English，再向下滚动显示简体中文；地区变体没有额外勾选。列表长度需要拆图，原图没有拼接。额外 Cook 目录与 Entry 地图的完整展开图见[项目配置](/docs/08-mmorpg/configuration)。

~~~ini title="DefaultGame.ini"
[Internationalization]
+LocalizationPaths=%GAMEDIR%Content/Localization/MMO

[/Script/UnrealEd.ProjectPackagingSettings]
InternationalizationPreset=EFIGSCJK
!CulturesToStage=ClearArray
+CulturesToStage=en
+CulturesToStage=zh-Hans
+DirectoriesToAlwaysCook=(Path="/Game/Localization")
~~~

本机 `Engine/Source/Runtime/Core/Private/Misc/Paths.cpp` 的 `FPaths::GetGameLocalizationPaths()` 从 **GGameIni** 读取该数组。曾把路径写进 DefaultEngine.ini 时，资源编译成功，但新游戏进程重新初始化本地化后仍回退英文；因此需要用全新进程检查登录标题，不能只在已经手动加载过资源的进程中切一次中文。

Designer 默认字体使用 UE 复合字体。本机 `LegacySlateFontInfoCache.cpp:124–127` 无条件把 `Engine/Content/Slate/Fonts/DroidSansFallback.ttf` 加入默认复合字体的 **FallbackTypeface**，这是独立 `-game` / Client 可用的通用后备路径；同文件 `187–206` 的 `zh-Hans` 专用子字体则只在 **GIsEditor=true** 时配置。两者不能混用：编辑器中的中文预览不能单独证明打包 Client 的字体已包含。最终仍需检查暂存产物中的 Roboto 与 DroidSansFallback，并在实际 Client 查看中文。替换项目字体时，在自己的 Font 资产中配置中文 Unicode 范围对应的子字体与后备字体，不能只依赖 Windows 已安装字体。

## 在游戏内切换并验收

`WBP_Settings` 的 ChineseButton、EnglishButton 使用 Designer 布局。C++ 分别调用 `SetCurrentCulture("zh-Hans", true)`、`SetCurrentCulture("en", true)`，保存选择并刷新 ViewModel；已有面板保留激活状态与焦点。

本机 `KismetInternationalizationLibrary.cpp` 仅在 `!GIsEditor` 时把 Culture 写入 GameUserSettings。因此偏好保存测试要使用独立游戏进程或打包 Client；同一编辑器进程中的多个 PIE 世界还会共享文化，不能用于验证两名玩家独立选语言。

在编辑器里预览时，打开 **Edit → Editor Preferences**，搜索 **Preview Game Language**，选择简体中文，再重新进入 PIE；Designer 工具栏也提供游戏本地化预览语言。UE 的 `TextLocalizationManager` 对编辑器游戏文本有单独的预览加载流程，未启用目标语言预览时可能仍显示原生英文数据；仅观察到 `CurrentCulture=zh-Hans` 不能证明 PIE 已加载中文游戏资源。编辑器启动的 Standalone 还可能根据该预览设置自动追加 `-culture`，因此**偏好恢复**必须用下面脚本启动的全新独立进程，并确认命令行没有该覆盖参数。

本教程的 `scripts/mmorpg/Start-Lab.ps1` 给每个客户端分配独立的 `-GameUserSettingsINI=<该客户端配置文件>`。由于多进程启动用了 `-Multiprocess`，还必须加 **`-MultiprocessSaveConfig`**，否则 UE 5.8.1 的 `ConfigCacheIni.cpp` 会禁止配置写盘；两个客户端共用同一文件又会互相覆盖文化。脚本同时使用 `-windowed -ResX=1920 -ResY=1080 -ForceRes`，避免本机编辑器游戏窗口被可用桌面区域限制尺寸；实际视口尺寸仍需从原生运行记录核对。

自动复验使用 `./scripts/mmorpg/Invoke-RenderedShowcase.ps1`，需要后端运行且当前没有其他实验占用服务。它分别切换两客户端的语言、读取各自 INI，再启动**没有 `-culture` 覆盖**的新进程核对保存文化及登录标题。传入真实 `-ClientExecutable`、`-ServerExecutable` 时使用已 Cook 的二进制，命令见[打包运行步骤](/docs/08-mmorpg/run-lab)；此模式不传 `.uproject` 或 `-game`。不传可执行文件时仍为 Editor 开发验证路径，两者写入独立报告。

1. 以 **1920×1080、中等画质** 启动客户端，登录入服。
2. 打开 Settings，选简体中文，检查标题、返回、退出说明、状态文字和冷却。
3. 保持面板打开，选 English，确认按钮仍能继续键盘或手柄导航。
4. 打开退出确认框，检查两种语言的长句均能换行，取消后焦点回到设置面板。
5. 攻击目标、施法、获得药剂，检查经验、法力、物品数量与冷却格式。
6. 退出再启动，确认语言偏好保留。两个客户端选择不同语言，确认游戏状态仍同步。

## 排障与练习

角色名是玩家输入的数据，不加入翻译表，也不随界面语言替换。显示时使用 `FText::AsCultureInvariant` 保留原名；HTTP JSON 使用 UTF-8，数据库列为 text。账号标识仍采用项目规定的 ASCII 字母、数字与下划线，与角色显示名是两项不同的输入规则。

`scripts/backend/Test-InternationalizedData.ps1` 已在本机服务执行 4 项检查：`教学旅人·一`、`Élodie des bois`、`旅人の記録` 的创建响应及 PostgreSQL UTF-8 字节均与输入一致；退出后重新登录，三个角色名仍一致。测试自动删除其专用账号，结果在 `verification/backend-internationalized-data.json`。这不证明输入法交互或全部 Unicode 字体覆盖；中文输入法、候选框和实际角色选择控件仍需在图形客户端检查。

| 现象 | 依次检查 |
| --- | --- |
| 部分文字始终英文 | FText、String Table 引用、新原文的 Gather/Import/Compile |
| MISSING STRING TABLE ENTRY | 表路径、Key、保存与 Cook；Namespace 不等于资产 Table ID |
| 中文方框 | 控件实际 Font、中文子字体范围、字体暂存结果 |
| 编辑器中文但游戏英文 | 游戏文化、加载路径、locres；编辑器语言与游戏文化是两个设置 |
| 中文修改后丢失 | 是否只改生成 PO，随后被旧清单覆盖；更新受版本管理的译文 |
| 切换后溢出 | Auto/Fill、最大宽度、Auto Wrap Text、按钮内边距 |
| 参数原样显示 | 中英文格式参数是否一致，Compile 的格式验证日志 |

练习：为“背包已满”增加业务错误码映射，补英文原文与中文译文。完成流水线后分别触发两种语言的错误，记录控件、Key、预期文案和真实截图。
