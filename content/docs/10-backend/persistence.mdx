## 学习目标与前置条件

理解游戏服务器的权威状态如何变成 PostgreSQL 中的一次可重试写入。前置条件是角色租约流程以及 SQL 事务概念。本篇对应 `MMOPersistence.cpp` 的 `/v1/server/save` 分支，核对 UE 5.8.1 教学增量日期 2026-09-13。

## 完整快照接口

游戏服务器在角色入服时记录后端返回的 `version`，例如初始版本 0。保存使用服务器凭据，并携带当前租约：

```json
{
  "characterId":"<character-uuid>",
  "leaseToken":"<active-lease>",
  "serverId":"local-1",
  "expectedVersion":0,
  "requestId":"<new-request-uuid>",
  "state":{
    "level":2,
    "xp":42,
    "health":75,
    "mana":80,
    "inventory":[{"itemId":"potion","quantity":3}],
    "position":{"x":12,"y":34,"z":150}
  }
}
```

成功响应 `{"version":1}`。游戏服务器将本地已确认版本更新为 1。保存失败时不能提前增加版本，也不能为了消除冲突而盲目改用最新版本覆盖数据库。

`MMO::ValidateState` 要求快照字段完整；等级、经验和数量满足范围约束，库存不能出现重复 `itemId` 或负数数量，位置必须有限且处于教学允许范围。客户端不能自己上传这个快照，服务器应先从权威 PlayerState、GAS 和库存组件收集数据。

## 乐观版本检查

SQL 的关键条件是：

```sql
UPDATE characters
SET state = $3::jsonb, version = version + 1, updated_at = now()
WHERE id = $1::uuid AND version = $2::bigint
RETURNING version;
```

只有数据库版本与调用方预期一致时才更新。若一条旧保存晚于新保存到达，受影响行数为 0，后端返回 HTTP 409 `version_conflict`。库存、经验、生命、法力和位置在同一 JSONB 行更新中一起提交，不会出现经验已更新但库存仍停留在旧状态的部分保存。

每个角色应只有一个保存协调器，串行提交快照。保存期间又有状态变化时，标记“仍然脏”，等当前响应成功后再以新版本保存最新快照。玩家退出也要通过这个协调器等待最后写入，不能同时发出释放与保存。

## 幂等请求 ID

网络可能丢失响应，即使数据库已经成功提交。此时服务器应保留原始 `requestId`、`expectedVersion` 和完全相同的快照重试。

后端先查询 `save_requests`。同一个角色和请求 ID 已成功保存过，且租约和负载摘要一致时，直接返回原结果版本，不再次写入。相同 ID 却换了快照或预期版本，返回 409 `idempotency_conflict`，防止调用方错误复用操作标识。

负载先通过 PostgreSQL JSONB 转成规范文本再做摘要，因此 JSON 对象键的排列顺序不会改变一次重试的身份。角色更新和幂等结果插入在同一事务中提交；发生数据库错误时，`FTransaction` 析构回滚尚未提交的事务。

## 租约与版本各防什么

租约判断“这个服务器进程是否仍有写权限”，版本判断“这次保存是否基于当前持久化状态”，请求 ID 判断“这个操作是否已执行过”。它们不能互相替代。

旧服务器即使记住正确版本，租约到期后仍应被拒绝。合法租约也不能让一条旧版本保存覆盖新版本。合法的新版本请求在响应丢失后重试，也不能再次增加版本。

## 周期保存与退出

教学单区使用周期保存并在正常离服时最后提交。`/v1/server/release` 只释放租约，不暗中保存；调用者要确认最后写入成功再释放。若最后保存遇到数据库故障，记录待重试状态并报告失败，不应把“断开连接”当作“存档成功”。

后端重启后，会话、票据、租约和快照仍在 PostgreSQL。游戏服务器是否还能继续写入取决于租约是否过期。游戏服务器自身崩溃后，恢复到最后成功提交的快照；未提交的变化需要更高频保存或额外事件日志才能缩小损失窗口。

## 预期结果、排障与练习

测试脚本会保存经验 42、药水 3 个，再重复同一次请求，确认版本保持 1。它会改变负载复用同一 ID、用新 ID 提交旧版本、保存负数库存，然后重新加载，确认已提交快照没有变化。

练习：模拟先发保存 A、再发保存 B，但 B 先完成。设计游戏服务器串行保存队列，并解释发生 503 后为什么要保留 A 的请求 ID。进阶练习是用数据库事务实现玩家间交换，而不是分别覆盖两份客户端快照。
